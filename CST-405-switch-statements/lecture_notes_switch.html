Overview

By this point in CST-405 we have implemented if / if-else branching, giving our compiler the ability to choose between two paths. Real programs, however, regularly need to choose among many alternatives based on the value of a single expression. Cascading if-else-if chains work, but they become hard to read and can be inefficient. The switch statement solves this problem elegantly.

In this unit we will:

  • Compare it with if-else chains analytically
  • Understand fall-through and the break keyword
  • Explore how compilers lower switch to jump tables or binary search

Motivation — Why switch?

Consider a program that maps a numeric day-of-week code (0–6) to an action. Using if-else chains:

C — if-else chain (verbose) 
if      (day == 0) printString("Sunday");
else if (day == 1) printString("Monday");
else if (day == 2) printString("Tuesday");
else if (day == 3) printString("Wednesday");
else if (day == 4) printString("Thursday");
else if (day == 5) printString("Friday");
else if (day == 6) printString("Saturday");
else             printString("Invalid");

This is correct but has several problems as the number of cases grows:

Problems with Long if-else Chains

  • Readability: The repeated else if (x == ...) pattern is noise. The intent (select on a value) is buried inside the structure.
  • Repetition: The variable day is evaluated in every branch; with side effects that can cause bugs.
  • Performance (naive): A linear chain is O(n) in the worst case. With enough cases, a compiler cannot easily optimize it without additional analysis.
  • Maintainability: Adding or removing a case requires careful copy-paste and indentation management.

The switch statement was designed to express exactly this pattern — dispatch on the value of a single integral expression — more clearly and with a compiler-friendly structure that enables O(1) jump-table dispatch.

Historical Context

Multi-way branching has existed in hardware since the earliest computers. The conceptual lineage of the switch statement looks like this:

Era / LanguageConstructKey characteristic
1950s — AssemblyJMP table[reg] Raw jump table; programmer-managed
1960 — COBOLEVALUATE Pattern-matched multi-way branch
1964 — FORTRANComputed GOTO Jump to label indexed by integer expression
1972 — Cswitch / case Integral dispatch with fall-through; parent of most modern variants
1983 — Adacase Exhaustive; ranges allowed; no fall-through
1995 — Javaswitch / case C-style; later enhanced (Java 14+)
2000s — C#, Go, Rust, Swiftswitch / match Pattern matching, exhaustiveness checks, no implicit fall-through

Our minicompiler targets C-style switch semantics — the foundation that most modern languages either adopt or consciously diverge from.

Syntax & Anatomy

The complete C syntax for a switch statement:

C — switch grammar (informal) 
switch ( expression ) {
    case constant:
        statement-list
        break;          // optional — without it, falls through

    case constant:
        statement-list
        break;

    // ... more cases ...

    default:           // optional — matches anything else
        statement-list
        break;
}

Each component explained

switch ( expression )

The controlling expression. In C89/C99 this must be an integral type (int, char, enum). It is evaluated exactly once, and the result is compared against each case constant.

case constant:

A case label. The constant must be a compile-time integral constant expression (literal integer, character literal, or enum member). Two case labels in the same switch may not have the same value — this is a semantic error.

break

Transfers control to the statement immediately after the closing } of the switch body. Without a break, execution falls through into the next case label's body (see Fall-through).

default:

Matches when no case constant equals the controlling expression. Optional but strongly recommended. Can appear anywhere in the switch body (though by convention it is last).

Concrete example

C — complete switch example 
int score = 85;
char grade;

switch (score / 10) {
    case 10:
    case 9:
        grade = 'A';
        break;
    case 8:
        grade = 'B';
        break;
    case 7:
        grade = 'C';
        break;
    case 6:
        grade = 'D';
        break;
    default:
        grade = 'F';
        break;
}

Notice that case 10: has no body — it falls through to case 9:, so both a perfect 100 and a 90–99 score produce 'A'. The controlling expression score / 10 is evaluated once before any comparison occurs.

Execution Semantics

The step-by-step runtime behavior of a switch statement:

Evaluate controlling expression once
↓
Compare result against case constants (compile-time)
match found →
Jump to matching case label
→
Execute body
no match →
Jump to default: (if present)
no default →
Skip entire switch body
↓ (after break or body end)
Continue after switch }

Formal semantics (simplified)

Let e be the controlling expression value. The switch selects the first case label cᵢ such that e == cᵢ. If no such label exists, the default label is selected (if present). Execution then proceeds sequentially from the selected label, crossing any intermediate labels, until a break, return, or the end of the switch body is reached.

⚠

Key insight: The case labels are not independent branches in the way that else if blocks are. Once execution jumps to a label, it runs linearly through all subsequent statements until a break or return stops it. This is called fall-through.

Fall-Through Behavior

Fall-through is perhaps the most debated design decision in C-style switch statements. When a case body does not end with break, control falls into the body of the next case label — even though the controlling expression did not match that label.

C — intentional fall-through 
switch (cmd) {
    case 'q':
    case 'Q':                 // both 'q' and 'Q' execute the same body
        quit();
        break;

    case 's':
        save();               // save, then also backup (fall-through)
    case 'b':
        backup();
        break;
}

When fall-through is useful

  • Grouping multiple values to the same action ('q' and 'Q')
  • Performing common initialization across a sequence of cases
  • Implementing state machines where states naturally cascade

When fall-through is dangerous

  • Forgetting a break causes silent, hard-to-find bugs
  • Code changes in one case can silently break the next case
  • Violates the principle of least surprise for readers
💡

Modern languages learned from C: Java, C#, Go, Rust, and Swift all disable implicit fall-through by default, requiring an explicit keyword (fallthrough in Go/Swift) to opt in. C23 added the [[fallthrough]] attribute as a way to silence compiler warnings when fall-through is intentional.

The default Clause

The default clause is the switch statement's equivalent of the final else in an if-else chain. It matches any controlling-expression value that was not matched by a preceding case label.

Why always include default?

Defensive programming

A switch without a default silently does nothing when the value is unexpected. This makes bugs invisible. A default that logs an error, asserts, or throws an exception makes invalid states detectable immediately.

C — defensive default 
switch (state) {
    case STATE_IDLE:    handle_idle();    break;
    case STATE_RUNNING: handle_running(); break;
    case STATE_DONE:    handle_done();    break;
    default:
        fprintf(stderr, "Unknown state: %d\n", state);
        abort();
}

Placement: The C standard allows default to appear anywhere in the switch body, not just at the end. However, by convention and for readability, it is almost always placed last.

switch vs. if-else — Detailed Comparison

Criterion switch / case if-else chain
Expression type Integral only (int, char, enum) Any boolean expression
Comparison kind Equality only (==) Any relational / logical operator
Constant requirement Yes — case values must be compile-time constants No — conditions may be arbitrary expressions
Expression evaluated Once (at switch entry) Each condition evaluated independently
Performance potential O(1) via jump table when dense O(n) linear scan in worst case
Fall-through Yes (feature or hazard depending on use) No — each branch is independent
Exhaustiveness checking Via default (optional, runtime) Via final else (optional)
Readability (many branches) High Low
Compiler optimization Jump tables, binary search trees Branch prediction, short-circuit
🔧

Rule of thumb: Use switch when you have three or more cases comparing a single integral variable to compile-time constants. Use if-else for ranges, floating-point, string comparisons, or complex boolean conditions.

Pros & Cons

Advantages

  • Readability: Intent is immediately clear — "dispatch on this value"
  • Performance: Enables O(1) jump-table dispatch for dense integer ranges
  • Single evaluation: The controlling expression is evaluated exactly once, preventing accidental side effects
  • Grouped cases: Multiple values sharing one body are easy to express
  • Compiler optimization: Structured form lets compilers choose optimal dispatch strategy (jump table vs. binary search vs. linear)
  • Default handling: The default clause makes unmatched values explicit

Disadvantages

  • Type restriction: Only works with integral types in C; no ranges, no strings, no floating-point
  • Fall-through hazard: Omitting break silently introduces bugs
  • Constant requirement: Case values must be compile-time constants; computed case values are not allowed
  • Variable declarations: Declaring variables inside a switch body without additional braces is error-prone due to scope rules
  • No pattern matching: Unlike modern language constructs, C switch cannot match on structure or type of values

How Compilers Implement switch

Compilers do not always generate the same machine code for a switch statement. The choice of implementation strategy depends on the number of cases and the density of the case values.

Strategy 1 — Linear Scan (sparse, few cases)

For switches with very few cases (typically ≤ 3), the compiler may simply emit a sequence of compare-and-branch instructions, identical to what an if-else chain would produce. This has the advantage of simplicity and is optimal when the number of comparisons is small.

MIPS pseudo-code — linear scan for switch(x) with 2 cases 
    lw   $t0, x           # load controlling expr
    li   $t1, 1
    beq  $t0, $t1, case_1
    li   $t1, 2
    beq  $t0, $t1, case_2
    j    default
case_1:
    # body for case 1
    j    switch_end
case_2:
    # body for case 2
    j    switch_end
default:
    # default body
switch_end:

Strategy 2 — Jump Table (dense, many cases)

When case values form a dense integer range (e.g., 0 through 9 with few gaps), the compiler builds a jump table: an array of addresses, one per possible case value. The controlling expression is used as an index into this array, producing a single indirect jump. This achieves true O(1) dispatch.

Conceptual jump table layout for switch(x) cases 0..4 
# Data section
jump_table:
    .word case_0       # address for x == 0
    .word case_1       # address for x == 1
    .word case_2       # address for x == 2
    .word case_3       # address for x == 3
    .word case_4       # address for x == 4

# Code section
    lw   $t0, x
    bltz $t0, default      # bounds check: x < 0
    li   $t1, 4
    bgt  $t0, $t1, default  # bounds check: x > 4
    la   $t1, jump_table
    sll  $t0, $t0, 2         # multiply index by 4 (word size)
    add  $t1, $t1, $t0
    lw   $t2, 0($t1)          # load target address
    jr   $t2                  # jump to case

Strategy 3 — Binary Search Tree (sparse, many cases)

When there are many cases but they are sparse (large gaps between values), a jump table would waste memory. Instead, the compiler may emit a binary-search decision tree of comparisons, achieving O(log n) dispatch.

Compiler heuristics

GCC and Clang choose among these strategies based on the number of cases and the density ratio (number of cases / range size). If density > ~50%, a jump table is generated. Below that threshold, a binary search or linear scan is used.

Jump Tables — A Closer Look

A jump table exploits the fact that memory can be addressed like an array. By storing code addresses in a contiguous array, we can translate an integer value directly into a target address in constant time, regardless of the number of cases.

Prerequisites for a jump table

  • All case constants must be integers (or be mappable to a contiguous integer range)
  • The range max_case − min_case must be small enough that the table fits in memory
  • Bounds checking is required at runtime: values outside the range jump to default

Why jump tables are important in compiler design

Jump tables are a canonical example of a compiler transformation: the programmer writes high-level switch statements; the compiler emits low-level, heavily optimized dispatch code that the programmer would rarely write by hand. This is one of the clearest demonstrations of why compilers are worth building.

🔗

Connection to our minicompiler: In our implementation, we will generate the simpler linear-scan strategy (a sequence of compare-and-branch TAC instructions). This is correct for all inputs and straightforward to implement. A jump table optimization can be added later as an extension.

switch Through the Compiler Phases

Implementing switch requires changes in every phase of our minicompiler. Here is what each phase must do:

Phase 1

Lexer (scanner.l)

Add token rules for switch, case, default, and break. These are new keywords that must be recognized before the parser sees the input.

Phase 2

Parser (parser.y)

Add grammar rules for the switch statement, case label list, and individual case clauses. Construct an AST node of type NODE_SWITCH with children for the controlling expression and each case.

Phase 3

Semantic (semantic.c)

Verify: controlling expression is integral; case values are compile-time integer constants; no duplicate case values exist; break only appears inside a switch or loop.

Phase 4

TAC (tac.c)

Emit a sequence of IF_FALSE TAC instructions (one per case), each comparing the switch variable to a case constant and jumping to the corresponding case label. Emit a GOTO to the default or end label. Emit a break label at the end of the switch.

Phase 5

Code Gen (codegen.c)

Lower each TAC switch instruction to MIPS compare-and-branch sequences. Handle register spilling at every label (merge point), identical to how we handled if-statement merge points.

Phase 6

AST (ast.c/h)

Define NODE_SWITCH, NODE_CASE, and NODE_DEFAULT node types. Each NODE_CASE holds the constant value and a pointer to its body. NODE_SWITCH holds the expression and a list of cases.

TAC representation (conceptual)

Three-Address Code for: switch(x) { case 1: ...; case 2: ...; default: ... } 
# Evaluate controlling expression
    t0 = x

# Case dispatch (linear scan)
    IF_FALSE t0 == 1 GOTO L_case2_test
L_case1:
    ... body of case 1 ...
    GOTO L_switch_end     # break

L_case2_test:
    IF_FALSE t0 == 2 GOTO L_default
L_case2:
    ... body of case 2 ...
    GOTO L_switch_end     # break

L_default:
    ... default body ...
    GOTO L_switch_end

L_switch_end:

Examples

Example 1 — Simple dispatch

C
int x = 2;
switch (x) {
    case 1: printInt(10); break;
    case 2: printInt(20); break;
    case 3: printInt(30); break;
    default: printInt(-1);  break;
}
// Output: 20

Example 2 — Grouped cases (intentional fall-through)

C
int month = 4;
int days;
switch (month) {
    case 1: case 3: case 5: case 7:
    case 8: case 10: case 12:
        days = 31; break;
    case 4: case 6: case 9: case 11:
        days = 30; break;
    case 2:
        days = 28; break;
    default:
        days = -1; break;
}
// month=4 → days=30

Example 3 — switch in a function

C
int classify(int n) {
    switch (n % 3) {
        case 0: return 0;  // divisible by 3
        case 1: return 1;  // remainder 1
        case 2: return 2;  // remainder 2
        default: return -1; // unreachable, but safe
    }
}

Example 4 — Nested switch

C
switch (outer) {
    case 1:
        switch (inner) {     // inner switch: each break exits only the inner switch
            case 10: printInt(110); break;
            case 20: printInt(120); break;
        }
        break;              // exits outer switch
    case 2:
        printInt(200);
        break;
}

Common Pitfalls

Pitfall 1 — Missing break

The single most common switch bug. Without break, execution continues into the next case body. Enable compiler warning -Wimplicit-fallthrough (GCC/Clang) to catch unintentional fall-through.

Pitfall 2 — Duplicate case values

Having two case 5: labels in the same switch is a compile-time error in C. Our semantic analyzer must detect and report this.

Pitfall 3 — Variable declarations without braces

Declaring a variable inside a case body (without wrapping it in { }) causes a scope problem: the variable's initialization may be skipped if another case is matched. Always wrap case bodies with their own braces when declaring local variables.

Pitfall 4 — Floating-point or string switch

C does not allow switch on float, double, or char*. Attempting this is a type error. Our semantic checker must flag non-integral controlling expressions.

Pitfall 5 — break scope in nested switch/loop

A break inside a switch that is nested inside a loop exits the switch, not the loop. If you want to break out of the loop from inside a switch, use a flag variable, goto, or restructure the code.

Summary

Key Takeaways

  • A switch statement dispatches on the value of a single integral expression, evaluated exactly once.
  • case labels must be compile-time integer constants; duplicates are a semantic error.
  • Execution falls through case bodies unless a break or return terminates the current case.
  • The default clause is optional but should always be present for defensive programming.
  • Compilers translate switch statements to linear scans, jump tables, or binary-search trees depending on density and count of cases.
  • Implementing switch in our minicompiler requires changes in every phase: lexer, parser, semantic analyzer, TAC emitter, and MIPS code generator.
