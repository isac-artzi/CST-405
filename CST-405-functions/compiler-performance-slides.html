Optimization 1: Symbol Table

The Problem: Linear Search

❌ Current Implementation

// Linear search - O(n)
for(i = 0; i < count; i++) {
    if(strcmp(vars[i].name, name) == 0) {
        return vars[i].offset;
    }
}
return -1;

Problem: Gets slower with more variables

✅ Solution: Hash Table

// Hash lookup - O(1) average
unsigned int h = hash(name);
SymbolNode* node = buckets[h];
while(node) {
    if(strcmp(node->name, name) == 0)
        return node->offset;
    node = node->next;
}

Result: Constant time lookups!

Hash Table Implementation Details

Choosing a Good Hash Function

// DJB2 Hash Algorithm - Simple and effective
unsigned int hash(const char* str) {
    unsigned int hash = 5381;
    int c;

    while ((c = *str++)) {
        hash = ((hash << 5) + hash) + c; // hash * 33 + c
    }

    return hash % HASH_SIZE;  // HASH_SIZE = 211 (prime)
}

Why This Works Well:

  • Prime number size (211): Better distribution, fewer collisions
  • Multiplier 33: Good bit spreading properties
  • Simple operations: Fast execution

Optimization 2: Memory Pool for AST

The Problem: Memory Fragmentation

❌ Individual Allocations

// Each node = separate malloc
ASTNode* node = malloc(sizeof(ASTNode));
// Problems:
// - Fragmentation
// - Allocation overhead
// - Poor cache locality

✅ Pool Allocation

// Allocate from pool
ASTNode* node = ast_alloc(sizeof(ASTNode));
// Benefits:
// - Contiguous memory
// - No fragmentation
// - Better cache performance

How It Works:

  • Allocate large chunks (4KB) at once
  • Hand out small pieces from the chunk
  • Only allocate new chunk when current is full

Memory Pool Implementation

#define POOL_SIZE 4096  // 4KB chunks - fits in L1 cache

typedef struct MemPool {
    char* memory;        // The chunk of memory
    size_t used;         // How much we've used
    size_t size;         // Total size available
    struct MemPool* next; // Link to next pool
} MemPool;

void* ast_alloc(size_t size) {
    // Align to 8 bytes for performance
    size = (size + 7) & ~7;

    if (current_pool->used + size > POOL_SIZE) {
        // Need new pool
        allocate_new_pool();
    }

    void* ptr = current_pool->memory + current_pool->used;
    current_pool->used += size;
    return ptr;
}
Memory Savings: 30-50% reduction in total memory usage!

Optimization 3: TAC Peephole Optimization

Eliminating Redundant Operations

❌ Unoptimized TAC

t0 = 5
t1 = 10
t2 = t0 + t1
x = t2

4 instructions, 3 temporaries

✅ Optimized TAC

x = 15

1 instruction, 0 temporaries!

Optimization Patterns:

  • Constant Folding: Evaluate constant expressions at compile time
  • Copy Propagation: Replace copies with original values
  • Dead Code Elimination: Remove unused computations

Implementing Peephole Optimization

Pattern Matching Approach

// Pattern 1: Constant Folding
if (current->op == TAC_ASSIGN &&
    next->op == TAC_ASSIGN &&
    isConstant(current->arg1) &&
    isConstant(next->arg1)) {

    // Look for: t0 = 5; t1 = 10; t2 = t0 + t1
    if (third->op == TAC_ADD &&
        third->arg1 == current->result &&
        third->arg2 == next->result) {

        // Replace with: t2 = 15
        int result = atoi(current->arg1) + atoi(next->arg1);
        third->op = TAC_ASSIGN;
        third->arg1 = itoa(result);

        // Mark old instructions for removal
        current->op = TAC_NOP;
        next->op = TAC_NOP;
    }
}

Copy Propagation in Detail

Eliminating Unnecessary Copies

Before Optimization

x = 10
t0 = x     // Copy
t1 = t0    // Another copy
y = t1 + 5

After Copy Propagation

x = 10
y = x + 5  // Direct use
Result: 50% reduction in instructions, less register pressure!

Perfect Hash Function

// Perfect hash for our 3 keywords
struct keyword {
    char* word;

    {"return", RETURN}

Optimization 5: Register Allocation

Reducing Memory Access

❌ Stack-Based Code

lw $t0, -4($fp)   // Load x
lw $t1, -8($fp)   // Load y
add $t2, $t0, $t1
sw $t2, -12($fp)  // Store result
// 3 memory accesses!

✅ Register-Allocated Code

// x in $s0, y in $s1
add $s2, $s0, $s1
// 0 memory accesses!

Memory Access Cost:

  • Register access: 1 cycle
  • L1 cache: 4 cycles
  • Main memory: 100-200 cycles

LRU Register Allocation Strategy

typedef struct {
    char* reg_name;    // e.g., "$t0"
    char* var_name;    // Variable in this register
    int last_used;     // For LRU tracking
} Register;

char* allocate_register(char* var) {
    // 1. Check if variable already in a register
    for(reg : registers) {
        if(reg.var_name == var) return reg.reg_name;
    }

    // 2. Find free register
    for(reg : registers) {
        if(reg.is_free) {
            reg.var_name = var;
            return reg.reg_name;
        }
    }

    // 3. Evict LRU register
    Register* lru = find_lru_register();
    spill_to_stack(lru);  // Save old value
    lru.var_name = var;
    return lru.reg_name;
}

Optimization 6: String Interning

Eliminating Duplicate Strings

❌ Without Interning

// Same identifier "count" appears 10 times
"count" → malloc(6) // 6 bytes
"count" → malloc(6) // 6 bytes
"count" → malloc(6) // 6 bytes
...
// Total: 60 bytes + overhead

✅ With Interning

// All references point to same string
"count" → pool[0] // 6 bytes once
"count" → pool[0] // Same pointer
"count" → pool[0] // Same pointer
...
// Total: 6 bytes!
Benefits: 20-40% memory savings, faster string comparisons (pointer equality)

String Pool Implementation

char* intern_string(const char* str) {
    // 1. Hash the string
    unsigned int h = hash(str);

    // 2. Check if already interned
    StringNode* node = buckets[h];
    while(node) {
        if(strcmp(node->str, str) == 0) {
            return node->str;  // Found it!
        }
        node = node->next;
    }

    // 3. Add new string to pool
    char* interned = pool + pool_used;
    strcpy(interned, str);
    pool_used += strlen(str) + 1;

    // 4. Add to hash table
    add_to_hash_table(h, interned);

    return interned;
}

Common Implementation Pitfalls

What to Watch Out For

  • Hash Collisions: Poor hash function → O(n) worst case
    • Solution: Use prime table sizes, good hash functions
  • Memory Pool Fragmentation: Variable-sized allocations
    • Solution: Separate pools for different sizes
  • Register Spilling: Too aggressive allocation
    • Solution: Profile-guided allocation
  • Over-optimization: Complex code for minimal gain
    • Solution: Focus on hotspots (80/20 rule)
  • Platform Dependencies: Code that only works on one OS
    • Solution: Use #ifdef for platform-specific code

Architecture-Specific Optimizations

Apple Silicon vs x86_64

Apple M1/M2 Optimizations

  • 16-byte alignment preferred
  • Larger register file (31 GPRs)
  • Better branch prediction
  • Unified memory architecture

x86_64 Optimizations

  • 8-byte alignment usually sufficient
  • Smaller register file (16 GPRs)
  • Complex addressing modes
  • SIMD opportunities (SSE/AVX)
// Conditional compilation for architecture
#ifdef __aarch64__  // Apple Silicon

    #define NUM_REGISTERS 31
#else  // x86_64

    #define NUM_REGISTERS 16
#endif
