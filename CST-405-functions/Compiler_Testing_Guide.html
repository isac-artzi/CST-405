C-Minus Compiler Testing and Debugging Guide

Comprehensive Guide for Testing Your Compiler Implementation

Overview

This guide will walk you through the process of thoroughly testing and debugging your C-Minus compiler implementation. You will test your compiler using two comprehensive test files that progressively introduce language features, verify the correctness of each compilation phase, measure performance, and audit critical compiler components.

Testing is not just about finding bugs—it's about understanding how your compiler transforms source code through each phase and ensuring the correctness of the final output.

1. Test Files Overview

You have been provided with two comprehensive test files that progressively test your compiler's capabilities:

Test File 1: test_functions_only.cm

This file tests your compiler's ability to handle:

  • Multiple function definitions with various parameter counts
  • Complex arithmetic expressions using all operators (+, -, *, /)
  • Functions calling other functions (function composition)
  • Nested function calls in expressions
  • Array declarations and array access operations
  • Return statements with complex expressions
  • Void functions with output operations
  • Input/output operations

Note: This test file does NOT include control flow statements (if-statements or loops).

Test File 2: test_with_if_statements.cm

This file includes all features from Test File 1, PLUS:

  • If-else statements (single and nested)
  • Complex relational expressions (==, !=, <, <=, >, >=)
  • Nested if-statements (up to 4 levels deep)
  • If-statements containing function calls
  • Functions that use if-statements for conditional logic
  • Conditional array processing
  • Multiple decision paths and branching logic

⚠ Testing Strategy

Start with test_functions_only.cm to ensure your compiler correctly handles basic features before moving to test_with_if_statements.cm. If your compiler fails on the first test, do not proceed to the second test until those issues are resolved.

2. Compilation Process and Phase Outputs

Your compiler transforms C-Minus source code through multiple phases. You must capture and analyze the output from EACH phase to verify correctness.

Step-by-Step Compilation Testing

1Lexical Analysis (Scanning)

What happens: The scanner reads the source file character-by-character and produces a stream of tokens.

How to test:

$ ./minicompiler test_functions_only.cm output.s > compiler_output.txt 2>&1

What to capture:

  • Token stream (if your compiler outputs tokens during scanning)
  • Any lexical errors (unrecognized characters, invalid tokens)

Verification checklist:

  • All keywords are correctly identified (int, void, if, else, while, return)
  • All identifiers (variable/function names) are recognized
  • All numeric literals are tokenized correctly
  • All operators and delimiters are recognized
  • Comments are properly ignored
  • No lexical errors are reported

2Syntax Analysis (Parsing)

What happens: The parser reads tokens and builds a parse tree according to the C-Minus grammar rules.

What to capture:

  • Parse tree structure (if outputted)
  • Syntax error messages (if any)
  • Success/failure of parsing

Verification checklist:

  • Parser successfully completes without syntax errors
  • All function declarations are recognized
  • All statements are correctly parsed
  • Expression precedence is handled correctly (e.g., * before +)
  • Nested structures (function calls, if-statements) are properly parsed

3Abstract Syntax Tree (AST) Construction

What happens: The AST is built from the parse tree, representing the program's semantic structure.

How to verify AST: Add debug print statements in your AST generation code to output the tree structure.

💡 AST Verification Tips

  • Node Types: Verify each node has the correct type (NODE_BINOP, NODE_VAR, NODE_DECL, etc.)
  • Tree Structure: Check parent-child relationships are correct
  • Operator Precedence: Ensure multiplication/division are child nodes of addition/subtraction
  • Function Calls: Verify function call nodes contain correct function name and argument list
  • Expression Nesting: Complex expressions should form proper sub-trees

Example AST structure for: x = a + b * c;

NODE_ASSIGN
├── NODE_VAR (x)
└── NODE_BINOP (+)
    ├── NODE_VAR (a)
    └── NODE_BINOP (*)
        ├── NODE_VAR (b)
        └── NODE_VAR (c)

Verification checklist:

  • AST correctly represents program structure
  • All declarations appear in correct order
  • Function bodies contain correct statement sequences
  • Expressions are properly nested with correct precedence
  • Array accesses are represented correctly
  • If-statements (Test 2) have condition and then/else branches

4Semantic Analysis and Symbol Table

What happens: The compiler performs semantic checks and builds a symbol table tracking variables and functions.

What to capture:

  • Symbol table contents (variable names, types, scopes, offsets)
  • Semantic error messages (undefined variables, type mismatches, etc.)

Verification checklist:

  • All variables are declared before use
  • No duplicate variable declarations in same scope
  • Function calls reference declared functions
  • Function call argument counts match parameter counts
  • Array indices are properly handled
  • Return types match function declarations

5Three-Address Code (TAC) Generation

What happens: The AST is translated into TAC, a simplified intermediate representation.

How to output TAC: Your compiler should have a function to print TAC instructions (e.g., printTAC()).

Example TAC output:

1: DECL x
2: DECL y
3: DECL sum
4: x = 10
5: y = 20
6: t0 = x + y
7: sum = t0
8: PRINT sum

💡 TAC Verification Tips

  • Three-operand form: Each instruction should have at most 3 addresses (result, arg1, arg2)
  • Temporary variables: Complex expressions should generate temporaries (t0, t1, etc.)
  • Instruction sequencing: TAC instructions should be in correct execution order
  • Function calls: Verify PARAM, CALL, and return value retrieval instructions
  • Control flow (Test 2): Check LABEL, IF, GOTO instructions for if-statements
  • Array access: Verify offset calculations for array operations

Verification checklist:

  • All declarations appear before their use
  • Temporary variables are used for intermediate results
  • Complex expressions are broken down into simple operations
  • Function calls include proper PARAM and CALL instructions
  • Labels and jumps (Test 2) are correctly generated
  • No undefined variables in TAC

6TAC Optimization

What happens: Optimization passes improve the TAC by eliminating redundancies.

Optimization techniques to verify:

Optimization Example
Constant Folding Before: t0 = 10 + 20
After: t0 = 30
Copy Propagation Before: x = 5; y = x;
After: x = 5; y = 5;
Dead Code Elimination Before: t0 = x + y; t0 = 10;
After: t0 = 10;

💡 Optimization Verification Tips

  • Compare before/after: Print TAC before and after optimization
  • Count instructions: Optimized TAC should have fewer or equal instructions
  • Verify correctness: Optimization must not change program semantics
  • Check edge cases: Ensure optimization doesn't break function calls or control flow

Verification checklist:

  • Constant expressions are evaluated at compile-time
  • Redundant temporary variables are eliminated
  • Unused instructions are removed
  • Optimized code produces same results as unoptimized code
  • Function calls and control flow remain correct

7MIPS Code Generation

What happens: TAC is translated into MIPS assembly code.

How to test: Compile and run the MIPS code using MARS or SPIM simulator.

$ ./minicompiler test_functions_only.cm output.s
$ java -jar Mars.jar output.s

Example MIPS output:

.data
.text
.globl main
main:
    addi $sp, $sp, -400      # Allocate stack
    li $t0, 10               # x = 10
    sw $t0, 0($sp)           # Store x
    li $t0, 20               # y = 20
    sw $t0, 4($sp)           # Store y
    lw $t0, 0($sp)           # Load x
    lw $t1, 4($sp)           # Load y
    add $t0, $t0, $t1        # x + y
    sw $t0, 8($sp)           # Store sum
    lw $t0, 8($sp)           # Load sum
    move $a0, $t0            # Prepare for print
    li $v0, 1                # Print integer syscall
    syscall
    addi $sp, $sp, 400       # Deallocate stack
    li $v0, 10               # Exit
    syscall

💡 Code Generation Verification Tips

  • Stack management: Verify stack pointer is correctly adjusted
  • Variable offsets: Each variable should have unique, correct offset
  • Register usage: Check temporary registers ($t0-$t9) are used properly
  • Function calls: Verify $ra (return address) is saved/restored
  • System calls: Check correct syscall codes for I/O operations
  • Labels and jumps: Verify control flow uses correct labels

Verification checklist:

  • MIPS code assembles without errors in MARS/SPIM
  • Stack is properly allocated and deallocated
  • All variables have correct stack offsets
  • Arithmetic operations produce correct results
  • Function calls work correctly (proper saving/restoring of registers)
  • Input/output operations function as expected
  • Program terminates properly with exit syscall

3. Performance Analysis and Metrics

Performance analysis helps you understand your compiler's efficiency and identify bottlenecks. You must measure and report performance metrics for your compiler.

Metrics to Measure

Metric Description How to Measure
Compilation Time Total time to compile source to MIPS Use time command: time ./minicompiler test.cm out.s
Phase Breakdown Time spent in each compiler phase Add timing code to each phase using clock() or gettimeofday()
TAC Instructions Number of TAC instructions generated Count instructions before and after optimization
Optimization Effectiveness Percentage reduction in TAC instructions Calculate: (original - optimized) / original * 100
MIPS Instructions Number of assembly instructions generated Count lines in output .s file (excluding comments/labels)
Symbol Table Size Number of symbols stored Report symbol count from symbol table
Memory Usage Peak memory consumption during compilation Use /usr/bin/time -v (Linux) or Activity Monitor (macOS)

Implementing Performance Measurement

Add timing code to your compiler's main function:

#include <time.h>

int main(int argc, char** argv) {
    clock_t start_total, end_total;
    clock_t start_phase, end_phase;
    double time_lex, time_parse, time_tac, time_opt, time_codegen;

    start_total = clock();

    // Lexical Analysis
    start_phase = clock();
    yyparse();
    end_phase = clock();
    time_lex = ((double)(end_phase - start_phase)) / CLOCKS_PER_SEC;

    // TAC Generation
    start_phase = clock();
    TACInstr* tac = generateTAC(root);
    end_phase = clock();
    time_tac = ((double)(end_phase - start_phase)) / CLOCKS_PER_SEC;

    // Optimization
    int tac_count_before = countTAC(tac);
    start_phase = clock();
    tac = optimizeTAC(tac);
    end_phase = clock();
    time_opt = ((double)(end_phase - start_phase)) / CLOCKS_PER_SEC;
    int tac_count_after = countTAC(tac);

    // Code Generation
    start_phase = clock();
    generateMIPS(tac);
    end_phase = clock();
    time_codegen = ((double)(end_phase - start_phase)) / CLOCKS_PER_SEC;

    end_total = clock();
    double time_total = ((double)(end_total - start_total)) / CLOCKS_PER_SEC;

    // Print performance report
    printf("\n=== COMPILER PERFORMANCE REPORT ===\n");
    printf("Total compilation time: %.4f seconds\n", time_total);
    printf("Lexical analysis: %.4f seconds\n", time_lex);
    printf("TAC generation: %.4f seconds\n", time_tac);
    printf("Optimization: %.4f seconds\n", time_opt);
    printf("Code generation: %.4f seconds\n", time_codegen);
    printf("TAC instructions (before opt): %d\n", tac_count_before);
    printf("TAC instructions (after opt): %d\n", tac_count_after);
    printf("Optimization reduction: %.2f%%\n",
           (tac_count_before - tac_count_after) * 100.0 / tac_count_before);

    return 0;
}

Performance Benchmarking

Create a performance comparison table for both test files:

Metric Test File 1 Test File 2 Notes

TAC Instructions (before) _________ _________ Test 2 should have more due to if-statements
TAC Instructions (after) _________ _________ Should be reduced after optimization

⚠ Performance Red Flags

  • Compilation takes > 5 seconds: Possible inefficiency in symbol table lookup or AST traversal
  • Optimization increases instruction count: Bug in optimization logic
  • Memory usage > 100MB: Possible memory leak
  • Optimization rate = 0%: Optimization not working or no optimizable patterns found

5. Scope Management and Type System Audit

Critical compiler components like scope management, type checking, and type coercion require thorough auditing. This section guides you through a systematic review of these essential features.

Scope Management Audit

What is scope management? Scope determines where variables and functions are visible and accessible in the program.

Audit Questions

  1. Does your compiler support global and local scopes?
    • Global scope: functions and global variables
    • Local scope: function parameters and local variables
  2. Can you handle nested scopes?
    • Compound statements create new scopes
    • If-statement blocks may have separate scopes
  3. Is variable shadowing handled correctly?
    • Local variable can shadow global variable with same name
    • Inner scope can shadow outer scope

Testing Scope Management

Create a test case:

int x;  /* Global x */

int foo(int x) {  /* Parameter x shadows global x */
    int y;
    y = x + 1;  /* Should use parameter x, not global x */
    return y;
}

void main(void) {
    int x;  /* Local x shadows global x */
    x = 10;
    output(foo(x));  /* Should pass local x to foo */
}

💡 Scope Audit Tips

  • Symbol table structure: Use a stack of hash tables, one per scope level
  • Scope entry/exit: Push new table when entering scope, pop when exiting
  • Lookup order: Search from innermost scope to outermost
  • Debug output: Print symbol table with scope levels for each variable
  • Test thoroughly: Create test cases with same variable names in different scopes

Type System Audit

C-Minus is a simply-typed language with int and void types. Your compiler must enforce type rules.

Type Checking Audit Questions

  1. Are all variables typed correctly?
    • Variables declared with proper types
    • Types stored in symbol table
  2. Are function return types checked?
    • void functions should not return values
    • int functions must return int expressions
  3. Are function argument types checked?
    • Function calls must match parameter types
    • Array parameters correctly identified
  4. Are operator type rules enforced?
    • Arithmetic operators require int operands
    • Relational operators produce boolean-like results

Testing Type Checking

Test cases to verify type checking (these should produce errors):

/* Test 1: void function returning value */
void foo(void) {
    return 5;  /* ERROR: void function cannot return value */
}

/* Test 2: int function not returning value */
int bar(void) {
    int x;
    x = 10;
    /* ERROR: missing return statement */
}

/* Test 3: Type mismatch in assignment */
int x;
x = foo();  /* ERROR: cannot assign void to int */

/* Test 4: Wrong argument count */
int add(int a, int b) {
    return a + b;
}

void main(void) {
    output(add(5));  /* ERROR: missing second argument */
}

Type Casting and Coercion Audit

Note: C-Minus does not support explicit type casting (no float, double, or type casts). However, you should be aware of implicit conversions.

Audit Questions

  1. Are all integer operations handled consistently?
    • Division produces integer result (truncation)
    • No overflow checking required (but good to be aware)
  2. Are boolean conditions handled properly?
    • Relational operators (==, <, >, etc.) produce 0 or 1
    • If-conditions treat non-zero as true, zero as false

Memory Management Audit

Audit Questions

  1. Are all dynamically allocated structures freed?
    • AST nodes
    • TAC instructions
    • Symbol table entries
  2. Are there any memory leaks?
    • Run with valgrind (Linux) or Instruments (macOS)
    • Check for "still reachable" or "definitely lost" memory
  3. Are string copies managed correctly?
    • Use strdup() for copying strings
    • Free duplicated strings when done
$ valgrind --leak-check=full ./minicompiler test.cm output.s

Conducting a Systematic Audit

Follow this structured approach to audit your compiler:

Step 1: Code Review

  • Review symbol table implementation line-by-line
  • Check for proper scope handling in lookup and insert functions
  • Verify type information is stored and retrieved correctly
  • Look for edge cases that might not be handled

Step 2: Create Targeted Test Cases

  • Write small test programs that specifically test scope rules
  • Create tests with deliberate type errors
  • Test boundary conditions (max variables, deep nesting)

Step 3: Trace Execution

  • Add debug prints showing scope entry/exit
  • Print symbol table contents at each scope level
  • Show type checking decisions
  • Trace variable lookups and show which scope was used

Step 4: Stress Testing

  • Test with maximum nesting depth
  • Test with many variables in same scope
  • Test with recursive functions
  • Test with large array sizes

✓ Audit Success Criteria

  • All scope test cases pass correctly
  • Type errors are caught and reported with clear messages
  • No segmentation faults or crashes during compilation
  • Symbol table correctly reflects program structure
  • Memory leaks are zero or minimal

Common Pitfalls to Avoid

  • Not freeing memory: Always free dynamically allocated nodes/instructions
  • Incorrect operator precedence: Multiplication must be evaluated before addition
  • Stack offset errors: Each variable needs unique offset, calculated correctly
  • Not saving $ra: Function calls must save/restore return address register
  • Ignoring semantic checks: Type checking and scope validation are critical
  • Over-optimizing: Optimization should never change program behavior
  • Hardcoding values: Use symbol table for variable offsets, not hardcoded values

Best Practices for Testing

  1. Test incrementally: Test each phase before moving to the next
  2. Start simple: Begin with basic test cases, then increase complexity
  3. Use version control: Commit working code before making changes
  4. Document as you go: Don't wait until the end to write reports
  5. Compare with reference: If available, compare your output with reference implementation
  6. Test edge cases: Empty programs, single statements, deeply nested structures
  7. Automate testing: Create shell scripts to run multiple tests automatically
