I. GENERAL GRADING PHILOSOPHY
================================================================================

This course emphasizes both theoretical understanding and practical
implementation of compiler construction. Students are provided with:
  - Detailed examples
  - Step-by-step directions
  - Extensive in-class exercises
  - Comprehensive documentation

THEREFORE: Grading must be STRICT and thorough. Students have all the
resources they need to succeed at a high level.

KEY PRINCIPLES:
1. Consistency: Apply the same standards to all students
2. Thoroughness: Actually run and test submitted code
3. Documentation: Clearly note deductions and reasons
4. Fairness: Grade what was submitted, not potential
5. Strictness: High expectations because of extensive support provided

II. LAB ASSIGNMENT GRADING
================================================================================

A. GRADING SCALE FOR LAB QUESTIONS
-----------------------------------

Each lab question should be graded on a simple scale:

FULL POINTS:
  - Answer demonstrates substantial engagement with the material
  - Content is relevant to the question asked
  - Shows clear understanding (even if not perfect)
  - Reasonable effort is evident
  - Key concepts are addressed

1 POINT (Partial Credit):
  - Minimal effort shown
  - Answer is present but lacks substance
  - Shows some engagement but misses key concepts
  - Incomplete but attempted

0 POINTS:
  - No answer provided
  - Answer is completely off-topic
  - Copy-pasted without understanding
  - Plagiarized content
  - Nonsensical or joke responses

B. SUBMISSION DEADLINE POLICY
------------------------------

STRICT DEADLINE ENFORCEMENT:
  - If lab questions are NOT submitted by the due date → ASSIGN 0
  - No exceptions
  - No partial credit for late labs
  - Due dates are clearly posted in the course schedule

How to check submission time:
  1. Check the timestamp on the submission platform
  2. Verify against the posted due date/time
  3. If even 1 minute late → 0 points

C. LAB GRADING WORKFLOW
-----------------------

For each lab submission:

1. Check submission timestamp
   - Late? → STOP. Assign 0 for entire lab. Add comment:
     "Not submitted by due date. Late labs receive 0 points per syllabus."

2. For on-time submissions, grade each question:
   - Read the question prompt carefully
   - Read the student's answer
   - Ask: "Does this show substantial, relevant engagement?"
     YES → Full points
     SOMEWHAT → 1 point (use sparingly)
     NO → 0 points

3. Provide brief feedback:
   - For full points: "Good understanding demonstrated."
   - For 1 point: "Answer lacks depth. Review [topic]."
   - For 0 points: "Answer missing/inadequate. See lecture notes on [topic]."

4. Total the score and record

III. COMPILER PROJECT GRADING
================================================================================

Projects are graded MUCH MORE STRICTLY than labs due to:
  - Extensive class time devoted to projects
  - Step-by-step instructions provided
  - Detailed examples and starter code given
  - Team-based work allowing collaboration
  - Performance analysis exercise completed in class

A. LATE SUBMISSION POLICY FOR PROJECTS
---------------------------------------

IMPORTANT: NO LATE PENALTIES FOR PROJECTS

  - Projects submitted late will NOT have points deducted
  - Grade based solely on quality and completeness
  - However, encourage on-time submission in feedback comments

B. PROJECT GRADING WORKFLOW
----------------------------

STEP 1: DOWNLOAD AND EXTRACT SUBMISSION
----------------------------------------
1. Download the complete project submission
2. Extract all files to a clean directory
3. Verify all required files are present:
   - Source code files (.c, .h, .l, .y)
   - Makefile
   - Test files
   - Documentation (README, design document, etc.)
   - Team member videos
   - Performance analysis document/section

MISSING FILES?
  → Note in grading comments
  → Deduct points according to rubric
  → If critical files missing (e.g., Makefile), may result in 0 for that section


STEP 2: IDENTIFY TEST FILES
----------------------------
Students should provide test files. Check for:
  - test.c, test*.c, or similar
  - Input files mentioned in documentation
  - Example programs in README

CRITICAL: You MUST test using STUDENT-PROVIDED test files
  - Different compiler implementations may behave slightly differently
  - Students' compilers are tailored to their test cases
  - If you use different test files, you may incorrectly mark as failing

If NO test files provided:
  → Use default test files (see Section IV)
  → Note in grading: "No test files provided. Used default tests."
  → Deduct points if rubric requires test files


STEP 3: BUILD THE PROJECT
--------------------------
1. Open terminal in project directory
2. Run: make clean (if Makefile exists)
3. Run: make

Expected outcomes:
  ✓ PASS: Compiles with no errors
  ✓ ACCEPTABLE: Compiles with warnings (check if warnings are serious)
  ✗ FAIL: Does not compile

If compilation FAILS:
  → Check if you have required dependencies (flex, bison, gcc)
  → Check if using correct platform (mention OS used in grading notes)
  → Try following any special build instructions in README
  → If still fails, assign 0 for implementation and note:
     "Project does not compile. Compilation errors: [paste errors]"
  → Still grade documentation and video sections


STEP 4: RUN THE COMPILER
-------------------------
Test the compiler with PROVIDED test files:

Example:
  ./compiler test.c output.s

For EACH test file:
  1. Run the compiler
  2. Check if it completes without crashing
  3. Check if output file is generated
  4. Examine the output file for correctness

Document your testing:
  Test 1 (test.c): ✓ PASS - Generates correct output
  Test 2 (test2.c): ✗ FAIL - Crashes on line 5
  Test 3 (test3.c): ✓ PASS - Works but output has minor formatting issues


STEP 5: VERIFY OUTPUT CORRECTNESS
----------------------------------
Depending on the project phase:

For Assembly Output (MIPS, x86, etc.):
  1. Check if output file is valid assembly syntax
  2. If MIPS simulator available, run the assembly code
  3. Verify output matches expected results
  4. Check for proper:
     - Stack management
     - Register usage
     - Function calling conventions
     - Labels and jumps

For TAC (Three-Address Code):
  1. Check if TAC is properly formatted
  2. Verify instructions are valid
  3. Check for proper temporary variable usage
  4. Verify optimization claims in documentation

For AST (Abstract Syntax Tree):
  1. Check if tree structure is printed/generated
  2. Verify correct node types
  3. Check proper parent-child relationships


STEP 6: EVALUATE AGAINST RUBRIC
--------------------------------
Go through EVERY rubric item systematically:

For each rubric item:
  [ ] Read the requirement carefully
  [ ] Check if feature is implemented
  [ ] Test the feature (don't just look at code)
  [ ] Assign points based on:
      - Full points: Feature works correctly
      - Partial: Feature partially implemented or has minor bugs
      - Zero: Feature missing or completely broken

Example Rubric Items (typical compiler project):
  - Lexical Analysis (Scanner): ___/15 pts
    * Tokenizes all required keywords
    * Handles identifiers and numbers
    * Reports lexical errors appropriately

  - Syntax Analysis (Parser): ___/15 pts
    * Correct grammar implementation
    * Proper error messages
    * Builds correct AST

  - Symbol Table: ___/25 pts
    * Proper scope management
    * Correct variable lookups
    * Function signature tracking

  - Intermediate Code (TAC): ___/15 pts
    * Correct TAC generation
    * Proper instruction format

  - Optimization: ___/10 pts
    * At least one optimization working
    * Documented in code/report

  - Code Generation: ___/30 pts
    * Generates correct target code
    * Follows calling conventions
    * Proper stack management

  - Testing: ___/15 pts
    * Multiple test cases
    * Test coverage documented
    * Expected outputs provided

  - Documentation: ___/15 pts
    * Clear README
    * Design decisions explained
    * Known limitations listed

  - Code Quality: ___/10 pts
    * Clean, readable code
    * Good comments
    * No memory leaks (if checked)

BE STRICT:
  - "Works mostly" = partial credit, not full
  - "Almost done" = grade what's submitted, not what's intended
  - Missing features = 0 points, even if code is otherwise good


STEP 7: COMPILER PERFORMANCE ASSESSMENT (CRITICAL!)
----------------------------------------------------

*** IMPORTANT: THIS IS REQUIRED EVEN IF NOT EXPLICITLY IN RUBRIC ***

Students completed an extensive in-class exercise on compiler performance.
EVERY project should include performance analysis.

Check for:
  1. Performance metrics documented
     - Compilation time
     - Memory usage
     - Output code size
     - Optimization impact measurements

  2. Comparison data
     - Before/after optimization
     - Different test cases
     - Benchmarking results

  3. Analysis and interpretation
     - Discussion of results
     - Explanation of performance characteristics
     - Identification of bottlenecks

WHERE TO LOOK:
  - Separate performance document (performance.pdf, analysis.txt)
  - Section in main documentation
  - README section titled "Performance Analysis"
  - Spreadsheet with benchmark data

GRADING PERFORMANCE SECTION:
  Full credit (10-15 pts, even if not in rubric):
    - Comprehensive measurements
    - Clear presentation (tables/graphs)
    - Thoughtful analysis

  Partial credit (5-7 pts):
    - Basic measurements present
    - Minimal analysis
    - Incomplete data

  Zero points:
    - No performance analysis included
    - Superficial "it runs fast" statements without data

DEDUCTION GUIDELINES:
  If performance analysis completely missing:
    → Deduct 10-15% of total project grade
    → Add comment: "Performance analysis required but not included.
                    This was covered extensively in class exercise."


STEP 8: EVALUATE DOCUMENTATION
-------------------------------

Documentation must show CLEAR and DEEP understanding.

Not sufficient to just have documentation - it must demonstrate:
  ✓ Understanding of design decisions made
  ✓ Knowledge of how different components interact
  ✓ Awareness of limitations and tradeoffs
  ✓ Ability to explain technical concepts clearly

Evaluate these aspects:

A. COMPLETENESS
  - All required sections present
  - No major topics omitted
  - Addresses all rubric requirements

B. CLARITY
  - Well-organized structure
  - Clear writing
  - Appropriate technical terminology used correctly
  - Diagrams/examples where helpful

C. DEPTH OF UNDERSTANDING
  ** THIS IS CRITICAL **

  Surface-level (insufficient):
    "We implemented a symbol table to store variables."
    → Shows WHAT but not WHY or HOW

  Deep understanding (good):
    "We implemented a hierarchical symbol table using a stack of
     scope structures. Each scope contains a hash table for O(1)
     lookups and a parent pointer for nested scope resolution.
     This design allows us to handle function-level scoping and
     variable shadowing. We chose hash tables over linear search
     to optimize lookup time in programs with many variables."
    → Shows WHAT, WHY, HOW, and TRADEOFFS

  Look for:
    - Explanation of design choices
    - Discussion of alternatives considered
    - Understanding of time/space complexity
    - Awareness of edge cases
    - Recognition of limitations

D. TECHNICAL ACCURACY
  - Correct use of terminology
  - Accurate descriptions of algorithms
  - No major technical errors
  - Appropriate references to course concepts

DOCUMENTATION GRADING:
  Full points: Complete, clear, demonstrates deep understanding
  70-90%: Complete but superficial, or incomplete but good depth
  50-70%: Significant gaps in completeness or understanding
  Below 50%: Minimal documentation or shows lack of understanding
  0%: No documentation or completely inadequate


STEP 9: EVALUATE TEAM MEMBER VIDEOS
------------------------------------

*** EVERY TEAM MEMBER MUST SUBMIT A VIDEO ***

Video requirements typically include:
  - Demo of compiler in action
  - Explanation of implementation
  - Discussion of challenges and solutions
  - Walkthrough of code
  - Duration: typically 5-10 minutes

GRADING POLICY:
  1. Check that EACH team member submitted their own video
  2. Grade the team's project as a whole
  3. BUT: If a team member's video is MISSING:
     → Deduct points ONLY from that individual member's grade
     → Other team members are not penalized

Deduction for missing video:
  → Typically 10-20% of total project grade
  → Apply ONLY to the member who didn't submit
  → Add note: "[Name]'s video not submitted. 15% deduction applied
               to [Name]'s grade only. Per syllabus, all team members
               must submit individual videos."

VIDEO QUALITY EVALUATION:

  Evaluate EACH video for:

  A. DEMONSTRATION
     - Actually runs the compiler
     - Shows multiple test cases
     - Demonstrates key features
     - Shows both successes and handles errors

  B. TECHNICAL EXPLANATION
     - Clearly explains implementation
     - Discusses architecture/design
     - References specific code sections
     - Uses correct terminology

  C. DEPTH OF UNDERSTANDING
     ** CRITICAL - Same as documentation **

     Poor video (low points):
       - Just reads through code line by line
       - Superficial explanations
       - Can't explain why things were done
       - Unclear on how pieces fit together

     Good video (full points):
       - Explains high-level architecture first
       - Discusses design decisions and tradeoffs
       - Demonstrates understanding of compiler phases
       - Can explain how components interact
       - Discusses challenges faced and solutions
       - Shows awareness of limitations

  D. PRESENTATION QUALITY
     - Clear audio
     - Visible screen/code
     - Well-organized presentation
     - Professional demeanor
     - Within time limits

  VIDEO GRADING SCALE (per team member):
    Full points:
      - Demonstrates clear, deep understanding
      - Good presentation quality
      - Covers all required topics

    70-90%:
      - Understanding evident but some superficiality
      - Minor presentation issues
      - Most topics covered

    50-70%:
      - Limited depth of understanding
      - Significant presentation issues
      - Some topics missing

    Below 50%:
      - Little understanding demonstrated
      - Poor presentation quality
      - Many topics missing

    0%:
      - Video not submitted
      - Video completely inadequate (< 1 minute, off-topic, etc.)

IMPORTANT: All team members should demonstrate understanding of the
ENTIRE project, not just "their part." Teams should work together.


STEP 10: CALCULATE FINAL GRADE
-------------------------------

1. Sum all rubric category scores
2. Add/subtract any additional points (performance analysis, etc.)
3. Apply individual deductions (missing videos) to specific students
4. Verify total matches rubric maximum
5. Record grade with detailed feedback

Example grade calculation:

Team: Alice, Bob, Carol
Base Project Score: 85/100

Alice: 85/100 (no deductions)
Bob: 85/100 (no deductions)
Carol: 70/100 (15 point deduction - no video submitted)

V. COMMON ISSUES AND HOW TO HANDLE THEM
================================================================================

ISSUE 1: Project compiles on student's machine but not on mine
---------------------------------------------------------------
SOLUTION:
  - Check README for platform-specific instructions
  - Verify you have correct versions of flex/bison/gcc
  - Try on different OS if available
  - Contact student to clarify build requirements
  - If truly incompatible, may need instructor guidance

DOCUMENT in grading notes:
  "Build attempted on [OS/platform]. Encountered [error].
   May need to verify build on different platform."


ISSUE 2: Student claims feature works but I can't make it work
---------------------------------------------------------------
SOLUTION:
  - Carefully re-read their documentation
  - Check if you're using correct test file format
  - Verify you're running correct commands
  - Watch their video to see how they demo it
  - If still fails, grade based on YOUR testing results
  - Document steps you took

GRADE POLICY: Grade what you can verify, not what they claim


ISSUE 3: Code is plagiarized or very similar between teams
-----------------------------------------------------------
SOLUTION:
  - Document the similarity carefully
  - Take screenshots of similar code sections
  - DO NOT assign grade - escalate to instructor immediately
  - Send email to instructor with:
    * Student/team names
    * Description of similarity
    * Evidence (screenshots, code snippets)
  - Instructor will handle academic integrity process


ISSUE 4: Project is incomplete but shows significant effort
------------------------------------------------------------
SOLUTION:
  - Grade based on what IS complete
  - Give partial credit where appropriate
  - Don't give points for effort alone - grade deliverables
  - In feedback, acknowledge effort but explain specific gaps:
    "Significant work evident, but [feature X] not functioning.
     To earn full credit, [specific requirement] must be met."


ISSUE 5: Team members blame each other for missing components
--------------------------------------------------------------
SOLUTION:
  - Grade what is submitted, not team dynamics
  - Do not get involved in team disputes
  - All team members receive same base project grade
  - Only individual deductions (videos) applied separately
  - If team dysfunction is severe, refer to instructor


ISSUE 6: Documentation/video shows misunderstanding of concepts
----------------------------------------------------------------
SOLUTION:
  - This IS gradable - reflect in scoring
  - Deduct points for incorrect explanations
  - Provide corrective feedback:
    "Explanation of [concept] is incorrect. [Brief correction].
     Review lecture notes on [topic]."
  - Remember: "Deep understanding" requirement is not met


ISSUE 7: Student requests regrade
----------------------------------
SOLUTION:
  - Review your grading notes and rubric
  - Re-test if necessary
  - If you find an error, correct it immediately
  - If your grading was correct, prepare explanation:
    * Reference specific rubric items
    * Show test results
    * Explain criteria applied
  - Respond professionally within 48 hours
  - If dispute continues, escalate to instructor


ISSUE 8: Performance analysis is present but inadequate
--------------------------------------------------------
SOLUTION:
  - Don't give 0 just because it's not perfect
  - Award partial credit based on:
    * Measurements present: 40%
    * Multiple test cases: 30%
    * Analysis and interpretation: 30%
  - Provide feedback on what's missing:
    "Performance analysis included but lacks [specific element].
     Should include [concrete suggestion]."

VII. CONTACT AND ESCALATION
================================================================================

WHEN TO CONTACT INSTRUCTOR:
  - Suspected plagiarism or academic integrity issues
  - Cannot build/run project after reasonable troubleshooting
  - Unclear rubric items or grading criteria
  - Student dispute that you cannot resolve
  - Technical issues preventing grading
  - Questions about deduction amounts
  - Unusual circumstances not covered in these guidelines

EXPECTED TURNAROUND TIME:
  - Labs: Grade within 1 week of submission deadline
  - Projects: Grade within 2 weeks of submission
  - Regrade requests: Respond within 48 hours

COMMUNICATION WITH STUDENTS:
  - Always professional and respectful
  - Be specific about deductions and reasons
  - Provide constructive feedback
  - Reference rubric items and course materials
  - Encourage office hours if they need clarification
  - Never argue or be defensive
  - If student is rude/hostile, end conversation and notify instructor

FEEDBACK BEST PRACTICES:
  ✓ Specific: "Symbol table does not implement scope hierarchy (Task 4)"
  ✗ Vague: "Symbol table needs work"

  ✓ Constructive: "Add error handling for undeclared variables. See parser.y example from lecture."
  ✗ Unhelpful: "Doesn't work"

  ✓ Balanced: "Good implementation of TAC generation. However, optimization phase not attempted."
  ✗ Only negative: "Optimization missing."
