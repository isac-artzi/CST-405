The Closure Problem

A closure is a function that remembers variables from the scope where it was created, even after that scope has returned. This is hard because the function and the captured variables must outlive the stack frame that created them.

The problem visualised
int base = 100;                  ← lives at -8($fp) in outer frame
g = fun(x) -> int { x + base };   ← needs base, but outer frame may be gone
/* when g(5) is called later, base's stack slot may be overwritten */

The solution: copy the captured values into a heap-allocated environment struct at closure creation time. The closure carries two values as a "fat pointer": the code address and the environment address. Inside the lambda, references to captured variables read from the environment struct instead of the stack.

Fat pointer layout
g variable on stack:
  [  code_ptr  ] ← address of _lambda_0  (4 bytes)
  [  env_ptr   ] ← address on heap       (4 bytes)
  total: 8 bytes per closure variable

Heap environment for this closure:
  [ base_copy  ] ← value of base at creation time (4 bytes)

Session 1 — First-Class Function Values

🎯

Goal: Parse fun(params) -> type { body }, generate a named function in MIPS (lambda lifting), and call it indirectly. No variable capture yet.

1

Lambda syntax

In scanner.l:

scanner.l
"fun"   { return FUN; }
"->"    { return ARROW; }

In parser.y, add a new expression rule:

parser.y
expr: FUN '(' param_list ')' ARROW type '{' stmt_list '}'
      { $$ = makeLambda($3, $6, $8); }

Reuse the existing param_list and type rules from function definitions. Add to ast.h: NODE_LAMBDA with a body child, param list, return type, and a captureList[] array (populated in session 2). Also add a generatedName[64] field that will hold the compiler-assigned name like _lambda_0.

2

Lambda lifting in tac.c

"Lambda lifting" means generating a regular named function for each lambda. In tac.c, maintain a static counter lambdaCount. When you encounter NODE_LAMBDA:

  1. Assign a generated name: _lambda_0, _lambda_1, etc.
  2. Emit a TAC_FUNC_BEGIN for the lambda (same as a regular function)
  3. Recursively generate TAC for the body
  4. Emit TAC_FUNC_END
  5. Return the lambda expression's value as a TAC_FUNC_ADDR of _lambda_0
⚠

Order matters: Lambda TAC must be emitted before the surrounding function's TAC, or place it in a separate queue and flush it at the end. In MIPS, all functions must be defined before any code that calls them (or you can use forward labels — check how your existing codegen.c handles function ordering).

3

Calling an anonymous function

For session 1, a closure variable is just a regular function pointer (one word, the code address — no fat pointer yet). Calling it works exactly like Extension 3 session 1: load the address, jalr. In session 2 you'll expand this to two words.

The key session 1 test: assign a lambda to a function pointer variable, call it multiple times with different arguments, see correct results. No outer variable references inside the lambda body yet.

✓ Session 1 Checkpoint

test_lambda1.c
int (*double_it)(int);
double_it = fun(int x) -> int { return x * 2; };
print(double_it(5));    /* 10 */
print(double_it(21));   /* 42 */

/* pass lambda as argument */
int apply(int (*f)(int), int v) { return f(v); }
print(apply(double_it, 7));   /* 14 */

/* lambda returned from function */
int (*makeLambda())(int) {
    return fun(int x) -> int { return x + 1; };
}
int (*incr)(int) = makeLambda();
print(incr(9));    /* 10 */
  • Generated MIPS contains a labeled _lambda_0 function with the correct body
  • Calling through the function pointer invokes the lambda body
  • Lambdas can be passed to and returned from functions

Session 2 — Variable Capture

🎯

Goal: When a lambda references a variable from the enclosing scope, allocate a heap environment struct at closure creation time, copy the captured values, and pass the environment as a hidden argument. Inside the lambda, reads of captured variables come from the environment.

1

Capture analysis in semantic.c

Walk the lambda body AST. For each identifier reference, look it up in the symbol table. If it resolves to a variable declared in an outer scope (depth less than the lambda's scope depth), add it to the lambda's captureList[].

semantic.c — capture detection sketch
void findCaptures(ASTNode *lambdaNode, int lambdaDepth) {
    /* walk all ID nodes in the body */
    /* for each ID: look up in symtab */
    /* if entry->scopeDepth < lambdaDepth → capture it */
    /* add to lambdaNode->captureList[] if not already there */
}

Store each captured variable's name and its outer-scope frame offset in the capture list. These will be copied into the environment at closure creation time.

2

Environment allocation in tac.c

Add a new TAC instruction TAC_ALLOC_ENV that allocates N × 4 bytes on the heap (using the same bump-pointer heap from Extension 1, or a fresh one). Emit one TAC_ENV_STORE instruction per captured variable to copy its current value into the environment.

TAC emitted at closure creation
t0 = ALLOC_ENV 4             ← allocate 1 slot (base is captured)
ENV_STORE t0[0] = base       ← copy current value of base into env
g_code = &_lambda_0          ← code pointer
g_env  = t0                  ← env pointer — store adjacent on stack

A closure variable g now occupies two stack words: the code address at offset and the env address at offset - 4 (or offset + 4, depending on your layout). Update the symbol table entry for closure-typed variables to allocate 8 bytes instead of 4.

3

Fat pointer calling convention

When calling through a closure variable, you must pass the environment pointer as a hidden last (or first) argument. The convention choice is yours — just be consistent. Let's use "last argument":

TAC for g(5) where g is a closure
PARAM 5               ← explicit argument
t1 = LOAD g_env       ← load env pointer
PARAM t1              ← hidden last argument
t2 = LOAD g_code      ← load code pointer
CALL_INDIRECT t2

Inside the generated lambda function body, the last parameter is the env pointer. Inside the lambda, any access to a captured variable like base becomes a load from the env: lw $t0, 0($env_reg). In codegen, when translating TAC for the lambda body, intercept reads of captured variables and redirect them to offset loads from the env parameter register.

💡

Simplification: For the two-session scope, implement capture by value (copy the value at creation time). This is simpler and still demonstrates the core concept. Capture by reference (sharing the actual variable) requires an additional level of indirection and is a challenge extension.

✓ Session 2 Checkpoint

test_closure.c
int base;
base = 10;

int (*adder)(int);
adder = fun(int x) -> int { return x + base; };
/* base is captured by value as 10 */

base = 999;   /* change base AFTER closure creation */
print(adder(5));    /* 15 — captured value 10, not 999 */
print(adder(20));   /* 30 */

/* two closures capturing the same variable */
base = 1;
int (*c1)(int) = fun(int x) -> int { return x + base; };
base = 2;
int (*c2)(int) = fun(int x) -> int { return x + base; };
print(c1(0));   /* 1 — captured when base was 1 */
print(c2(0));   /* 2 — captured when base was 2 */
  • Heap environment is allocated at closure creation, not at call time
  • Changing base after closure creation does not affect the captured value
  • Two closures capturing the same variable at different times have independent copies
  • Memory debugger (examine heap in MARS) shows the env struct with the correct value

Challenge Extensions

  • Implement capture by reference: the env struct stores the address of the variable, not its value — changes to base after creation are visible through the closure
  • Implement a makeCounter() function that returns a closure which increments a captured counter each time it is called
  • Support closures that capture other closures
