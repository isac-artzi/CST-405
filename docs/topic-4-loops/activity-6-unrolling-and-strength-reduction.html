Unrolling and Strength Reduction

Two optimizations you will not implement, done by hand so you can talk about them accurately.

All topics  ›  Topic 4  ›  Activity 6
Format pairsTime 45 min

The point

Two optimizations you will not implement, done by hand, so you can talk about them accurately.

Do this

  1. Unroll by hand. Take
    for (i = 0; i < 4; i = i + 1) { s = s + a[i]; }
    and write both the normal lowering and a fully unrolled version. Count the instructions in each, and count how many EXECUTE in each.
  2. Partial unrolling. Now unroll by 2 rather than fully. Write it. What has to be true about the trip count for this to be correct, and what extra code is needed when it is not?
  3. When does unrolling lose? Change the loop to 10,000 iterations and reason about it. Name two costs.
  4. Strength reduction. The array index does i * 4 every iteration. Rewrite the loop to keep a running address and add 4 each time instead. Count the instructions saved per iteration.
  5. Find it in the compiler. One strength reduction is already there: sll $t, $t, 2 instead of a multiply. Locate it in codegen.c and say why the compiler can always do that one safely.
On step 3

Code size, and instruction-cache pressure. A loop body that fitted in cache may not after unrolling, and a cache miss costs far more than the compare-and-branch you removed. This is why unrolling decisions in real compilers are driven by measured heuristics and not by a rule.

Deliverable

Both unrolled listings with instruction counts, your answer on partial unrolling, two named costs, the strength-reduced loop, and the line number of the existing strength reduction. Feeds Lab Question 21.
