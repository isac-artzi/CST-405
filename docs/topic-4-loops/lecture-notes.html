Structured control flow becomes labels and jumps — and then the optimizer stops being a lecture topic and starts producing numbers you can quote.

There are no loops in a machine

A CPU has exactly two control-flow instructions: jump somewhere, and jump somewhere if a register is zero. Every while, for, if and switch in every language you have used is a pattern of those two. Building them is called lowering, and it happens in phase 4.

    while (c) B                    for (init; c; upd) B
    ───────────                    ────────────────────
                                     <init>
  Lstart:                          Lstart:
      t = <c>                          t = <c>
      IF_FALSE t GOTO Lend             IF_FALSE t GOTO Lend
      <B>                              <B>
      GOTO Lstart                      <upd>
  Lend:                                GOTO Lstart
                                   Lend:

Read those two side by side. A for loop is a while loop with two extra pieces bolted on, which is why many compilers desugar for into while in the front end and reuse one lowering. Either approach is fine; be able to say which you chose and why.

Watch a loop lower

The source. Three lines that will become eleven instructions.

i = 0;
while (i < 3) {
    print(i);
    i = i + 1;
}

Anything before the loop is emitted first, unchanged.

i = 0

A label marks the top. Every iteration will come back here.

i = 0
Lstart:

The condition is an ordinary expression, so it produces a temporary holding 1 or 0.

i = 0
Lstart:
    t0 = i < 3

The test. This is the ONLY thing that makes it a loop rather than a straight line.

i = 0
Lstart:
    t0 = i < 3
    IF_FALSE t0 GOTO Lend

The body, lowered normally. Nothing about it knows it is inside a loop.

i = 0
Lstart:
    t0 = i < 3
    IF_FALSE t0 GOTO Lend
    PRINT i
    t1 = i + 1
    i = t1

The jump back, and the exit label. Done.

i = 0
Lstart:
    t0 = i < 3
    IF_FALSE t0 GOTO Lend
    PRINT i
    t1 = i + 1
    i = t1
    GOTO Lstart
Lend:
Test at the top, not the bottom

The condition is evaluated BEFORE the body, so a loop whose condition is false initially executes zero times. That is what while means. Emit the test at the bottom instead and you have accidentally implemented do-while — a real language, but not the one you documented.

break is a stack, and that is the whole implementation

break means jump to the exit label of the innermost thing I am inside. The compiler does not need to analyse anything to work that out: when it starts lowering a loop it pushes that loop's exit label, and when it finishes it pops. A break anywhere in between emits a jump to whatever is on top.

    push Lend_outer
        push Lend_inner
            break;      ->   GOTO Lend_inner      (top of stack)
        pop
        break;          ->   GOTO Lend_outer      (top of stack now)
    pop

Nesting falls out for free. So does the error case: if the stack is empty when a break is lowered, the program had a break outside any loop — and the semantic analyzer should already have said so, with a line number, using the same idea as a depth counter.

Now the optimizer earns its keep

Until this topic, optimization was a formality — straight-line code has little to remove. Loops change that, because an instruction inside a loop that runs 1,000 times costs 1,000 instructions.

Why one pass is not enough

The techniques feed each other. Watch three passes turn six instructions into two:

t0 = 2 * 3
x  = t0
t1 = x + 0
y  = t1
t2 = y * 1
print t2
t0 = 6            folded
x  = 6            propagated
t1 = x            algebraic (x + 0)
y  = x
t2 = y            algebraic (y * 1)
print t2
x = 6
y = 6             propagated through the copies
t2 = 6
print 6           propagated into the print
print 6            everything else was dead

no changes on pass 4 — fixed point reached

This is why optimizeTAC loops until a pass reports zero changes. Running to a fixed point is how real optimizers are structured, and it is why the order of techniques within a pass matters less than you would expect.

The safety rule you must not break

At a LABEL, forget every value you thought you knew. Control can arrive at a label from anywhere, so a fact established on one path is not a fact on another. Propagate a constant across a loop back-edge and you will produce a compiler that is correct on straight-line code and silently wrong on loops — the worst possible failure mode, because the tests you wrote in Topic 2 still pass.

Measuring it

Topic 4 asks you to quantify the gain. Two numbers are available and they measure different things:

MetricWhere to get itWhat it tells you
TAC instruction countthe optimizer's own reporthow much smaller the program got
Executed instruction countSPIM's statistics after a runhow much less work it actually does

They can diverge sharply. Removing one instruction from inside a loop that runs 300 times shrinks the code by one and the execution by 300. Removing twenty instructions of setup code that runs once shrinks the code by twenty and the execution by twenty. Say which you measured.

    # code size, from the compiler's own report
    TAC instructions   48 -> 31  (17 removed, 35.4% smaller)

    # work done, from SPIM
    spim -file bench.s
    # (QtSPIM shows an instruction count; spim -exception_file ... likewise)
What counts as a significant gain?

Lab Question 22 asks you to say, with reference to your own machine. Some anchors: a 5% reduction is inside the noise of most measurement setups and you should not claim it without repeating the run. A 30% reduction in executed instructions is a real result. A 10× result usually means you removed something that should not have been generated in the first place — which is a fine outcome, but the honest report says so rather than crediting the optimizer.

Two more techniques worth discussing (Lab Questions 21)

Loop unrolling

    for (i = 0; i < 4; i = i + 1)      s = s + a[0];
        s = s + a[i];              ->      s = s + a[1];
                                           s = s + a[2];
                                           s = s + a[3];

Removes four condition tests and four jumps, at the cost of four times the code. Worth it when the trip count is small and known; harmful when the loop body no longer fits in the instruction cache. Note that it requires knowing the trip count at compile time — which is why it pairs so naturally with constant propagation.

Strength reduction

Replace an expensive operation with a cheap one that computes the same thing: i * 4 becomes i << 2; a multiply inside a loop becomes an add on each iteration. Your array indexing already does the first one — find it in elementAddrReg.
