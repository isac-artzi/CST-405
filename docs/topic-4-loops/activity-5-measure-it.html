Measure It, and Defend the Number

Code size and work done are different numbers. Get both, repeat the run, and state a threshold you can justify.

All topics  ›  Topic 4  ›  Activity 5
Format pairs, at a laptopTime 50 minNeed SPIM, and your machine's specs

The point

Produce a number you would be willing to defend. Most reported speedups do not survive the question compared to what, measured how?

Do this

  1. Write a benchmark with a hot loop — a nested loop running a few thousand iterations. tests/t6_07_benchmark.cm is a starting point if you want one.
  2. Get the code-size numbers. Compile it and record the TAC instruction count before and after optimization, plus the per-technique scorecard.
  3. Get the work-done numbers. Run both versions in SPIM and record the executed instruction count for each. To get an unoptimized .s, temporarily point generateMIPSFromTAC at getUnoptimizedTAC().
  4. Put the four numbers in a table and compute both percentages. They will not match. Explain the gap in one sentence.
  5. Repeat the run three times. How much do the numbers move? Anything smaller than that spread is not a result.
  6. State a threshold. Given your machine and your measurement noise, what reduction would you call significant? Justify it with the numbers from step 5, not with a feeling.

Deliverable

A results table with all four numbers and both percentages, three repeated runs, your noise estimate, and a defended threshold. This is Lab Question 22 and a large part of the Project 6 performance section — do it properly now and reuse it in December.
