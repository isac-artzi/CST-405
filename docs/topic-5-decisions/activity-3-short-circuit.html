Short-Circuit or Not — Decide It

Two lowerings, a truth table, the bitwise-and trap, and a measurement.

All topics  ›  Topic 5  ›  Activity 3
Format pairsTime 50 min

The point

Short-circuit evaluation is a language design decision that most people inherit without noticing. Make it consciously, and measure what it costs.

Do this

  1. Write both lowerings on paper for a && b: the eager one and the short-circuiting one. Count instructions in each listing and instructions EXECUTED when a is false.
  2. Implement the eager version (this is what the TODOs describe) and confirm the truth tables:
    print(1 && 1);  print(1 && 0);  print(0 && 1);  print(0 && 0);
print(1 || 0);  print(0 || 0);  print(!0);  print(!5);
  3. Test the trap. print(2 && 1); must print 1, not 0. If it prints 0 you emitted a bitwise and without normalising. Fix it and explain the fix in one sentence.
  4. Measure. Write a loop that evaluates i > 100 && i < 200 ten thousand times where i is always 5. Record SPIM's executed-instruction count. How many of those instructions were wasted evaluating the second operand?
  5. Decide. Would you implement short-circuiting in your compiler? Under what change to the language would it stop being optional? Two sentences.
The answer to the second half of step 5

The moment expressions can have side effects. Add function calls in expressions — which you already have — and n != 0 && safeDivide(x, n) becomes a program whose correctness depends on the answer. At that point short-circuiting is not an optimization, it is part of the language's meaning.

Deliverable

Both lowerings with instruction counts, your eight truth-table results, your one-sentence fix for step 3, your measurement, and your two-sentence decision. Feeds Lab Question 24.
