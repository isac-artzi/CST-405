Decisions, the Dangling Else, and switch

if and else are two rules and one famous ambiguity. switch is one rule and one genuinely interesting code-generation choice.

if is the loop you already wrote, without the back edge

    if (c) T                       if (c) T else E
    ────────                       ───────────────
        t = <c>                        t = <c>
        IF_FALSE t GOTO Lend           IF_FALSE t GOTO Lelse
        <T>                            <T>
    Lend:                              GOTO Lend
                                   Lelse:
                                       <E>
                                   Lend:

If you built loops in Topic 4, you have already written every mechanism this needs. Which is the point: the fourth construct you lower is much cheaper than the first, and that is what the layered structure of this course was for.

The one thing to get right

The GOTO Lend at the end of the then-branch. Leave it out and control falls from the then-branch straight into the else-branch, so both run. The program still compiles, still runs, and is wrong in a way that a test with a false condition will not catch.

The dangling else

This is the most famous ambiguity in programming languages, and your grammar has it right now whether or not you have noticed.

    if (a) if (b) X else Y

    reading 1:   if (a) { if (b) X else Y }        <- else belongs to the INNER if
    reading 2:   if (a) { if (b) X } else Y        <- else belongs to the OUTER if

Both are valid derivations from the obvious grammar. They mean different things: with a true and b false, reading 1 runs Y and reading 2 runs nothing.

Every mainstream language picks reading 1 — else binds to the nearest if. Bison, left alone, also picks reading 1, because when it must choose between shifting the ELSE and reducing the inner if, it shifts. So the default is already correct. What is not correct is leaving a shift/reduce conflict in your grammar and hoping.

$ bison -d parser.y
parser.y: warning: 1 shift/reduce conflict

# bison resolved it by shifting, which happens to be what you wanted.
# It will resolve the NEXT one by shifting too — including the one you
# did not want. A grammar with unexplained conflicts is a grammar you
# have stopped reading.
%nonassoc LOWER_THAN_ELSE   /* a pseudo-token, lower precedence */
%nonassoc ELSE              /* declared later, so higher       */

if_stmt : IF '(' expr ')' stmt %prec LOWER_THAN_ELSE
        | IF '(' expr ')' stmt ELSE stmt
        ;
The rule  IF '(' expr ')' stmt  is given LOWER precedence
than the token ELSE.

So when the parser is sitting on a complete
    IF '(' expr ')' stmt
and the lookahead is ELSE, it compares:

    reduce using this rule   (precedence: LOWER_THAN_ELSE)
    shift the ELSE           (precedence: ELSE, which is higher)

Higher wins -> SHIFT -> the else attaches to the inner if.
Same outcome as the default, but now it is DECLARED, and
bison reports no conflict.

Why must %nonassoc LOWER_THAN_ELSE be written BEFORE %nonassoc ELSE?

Boolean operators, and the decision you are making by accident

&& and || have a property that + does not: in most languages they short-circuit. a && b does not evaluate b when a is false.

t0 = <a>
t1 = <b>            <- always evaluated
t2 = t0 && t1

MIPS, because `and` is BITWISE:
    sne  $t3, $t0, $zero      # normalise a to 0/1
    sne  $t4, $t1, $zero      # normalise b to 0/1
    and  $t5, $t3, $t4
t0 = <a>
t2 = 0
IF_FALSE t0 GOTO Lend       <- b is never evaluated if a is false
t1 = <b>
t2 = t1
Lend:

More instructions in the listing.
Fewer executed, whenever a is false.

Ours is eager, and that is a legitimate choice for a language with no side effects in expressions — no assignment operator, no ++. But the moment your language gains a function call in an expression, eager evaluation becomes observable: n != 0 && divide(x, n) will call divide with zero. Say in your write-up which you implemented and what would force you to change.

MIPS and/or are bitwise

2 & 1 is 0, but 2 && 1 is 1. If you emit and directly on the operands you will get the wrong answer for every value that is truthy but not exactly 1. Normalise each operand with sne $t, $x, $zero first. !x is just seq $d, $x, $zero.

switch, and the fall-through that falls out for free

A switch lowers naturally into two sections: a DISPATCH section that decides where to go, and a BODY section that is just the case bodies laid out one after another.

The source.

switch (x) {
    case 1: print(10); break;
    case 2:
    case 3: print(23); break;
    default: print(0); break;
}

Evaluate the controlling expression ONCE, into a hidden variable. If you re-evaluate it per case, a switch on a function call would call it n times.

DECL __sw0
__sw0 = x

The dispatch chain: one comparison per case label, in source order.

DECL __sw0
__sw0 = x
t0 = __sw0 == 1
IF_FALSE t0 GOTO Ltest1
GOTO Lbody1

...and so on for every case. Note case 2 and case 3 get separate tests, even though they will share a body.

Ltest1:
    t1 = __sw0 == 2
    IF_FALSE t1 GOTO Ltest2
    GOTO Lbody2
Ltest2:
    t2 = __sw0 == 3
    IF_FALSE t2 GOTO Ltest3
    GOTO Lbody3

If nothing matched, go to the default — or straight to the end if there is no default.

Ltest3:
    GOTO Ldefault

Now the bodies, in source order, with NO jump between them. That absence is fall-through: control simply runs off the end of one body into the next.

Lbody1: PRINT 10
        GOTO Lend        <- this is the `break`
Lbody2:                  <- empty body: case 2 falls straight into case 3
Lbody3: PRINT 23
        GOTO Lend
Ldefault: PRINT 0
        GOTO Lend
Lend:

break is a GOTO to Lend, taken from the same label stack the loops use. Which is why a break inside a switch inside a loop leaves the SWITCH and not the loop — the switch pushed its label more recently.

push Lend_loop
    push Lend_switch
        break;   ->  GOTO Lend_switch
    pop
pop

The alternative: a jump table

Instead of n comparisons, build an array of addresses indexed by the case value and jump indirectly. One bounds check and one indirect jump, regardless of how many cases.

Linear chainJump table
Cost of dispatchO(n) comparisonsO(1)
Cost in spaceO(n) instructionsO(range) words
case 1,2,33 comparisons3-word table
case 1, 1000, 500003 comparisonsa 50,000-word table
Good whenfew cases, or sparse valuesmany cases, dense values

Real compilers choose per switch, and often build a hybrid: a table for the dense cluster and comparisons for the outliers. We implement the linear chain because it is correct for every case-value distribution and it is twenty lines. Knowing why the other one exists is the part that matters.

MIPS vs ARM — what would actually change

Topic 5 asks you to compare code generation for the two. The useful answer is not a list of mnemonics; it is which parts of your compiler you would have to touch.

MIPS (what we emit)ARM (AArch32/64)
Registers32, by convention $t/$a/$s/$v16 (A32) or 31 (A64), similar conventions
Comparisonslt $d,$a,$b produces 0/1 in a registercmp a, b sets FLAGS; no result register
Branchbeq $t, $zero, L on a registerb.eq L on the flags set by the last cmp
Conditional executionnone — every conditional is a branchA32 predicates most instructions: addne, movgt
Callsjal puts the return address in $rabl puts it in LR — same idea, different name

So: your scanner, parser, AST, semantic analyzer, TAC generator and optimizer are all unchanged. Only codegen.c is rewritten — and within it, mostly mnemonicFor, the branch cases and the prologue/epilogue. That is the payoff for having an IR at all, and it is the single best thing to be able to say about your compiler's architecture.

The one place ARM changes more than the mnemonics

Conditional execution. On A32, if (a) x = 1; can compile to two instructions with no branch at all: cmp then movne. A back end that exploits that is not a transliteration of the MIPS one — it needs an if-conversion pass that decides when a branch is worth replacing with predicated code. That is a genuine architectural difference, not a naming one.
