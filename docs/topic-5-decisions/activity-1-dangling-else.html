Create the Dangling-Else Conflict, Then Fix It

Build the conflict on purpose, read parser.output, fix it three ways, and swap the declarations to see it break.

All topics  ›  Topic 5  ›  Activity 1
Format pairs, at a laptopTime 45 min

The point

Create the dangling-else conflict deliberately, read bison's report on it, then fix it two different ways and observe that only one of them is honest.

Do this

  1. Add the two if rules WITHOUT any precedence declarations. Build with bison -d -v parser.y and read the warning.
  2. Open parser.output and find the conflicted state. It shows the item set — what the parser had seen and what it could not decide. Copy that state into your notes.
  3. Test which way bison resolved it. Compile and run
    int main() {
    int x; int y;
    x = 1; y = 0;
    if (x > 0) if (y > 0) print(1); else print(2);
    return 0;
}
    It prints 2 if the else bound to the inner if, and nothing at all if it bound to the outer one. Which happened?
  4. Fix it properly with %nonassoc LOWER_THAN_ELSE and %nonassoc ELSE. Rebuild. The warning should be gone and the behaviour unchanged.
  5. Swap the two declarations. Predict what the test program prints now, then run it.
  6. Fix it a third way, on paper only: rewrite the grammar with matched_stmt and unmatched_stmt so that it is unambiguous with no precedence declarations at all. This is the classic textbook solution — write it out and say why you would or would not ship it.

Deliverable

The parser.output excerpt, what the test printed at each stage, and your unambiguous grammar from step 6 with a one-paragraph judgement. This is Lab Question 25 nearly verbatim.
