A compiler is a pipeline of small translations

A compiler turns text into machine code. Said that way it sounds like one enormous problem. It is not. It is six small ones, arranged so that each hands the next a representation that is a little further from how people write and a little closer to how machines run.

Read the diagram as a sequence of data structures, not a sequence of actions. That is the real content of the design:

PhaseInOutThe question it answers
1 · LexicalcharacterstokensAre these words in the language?
2 · Syntaxtokenssyntax treeDo those words form a sentence?
3 · Semanticsyntax treechecked treeDoes the sentence mean anything?
4 · IRchecked treethree-address codeWhat steps compute it?
5 · OptimizeTACsmaller TACWhich steps are unnecessary?
6 · CodeGenTACMIPS assemblyHow does this machine do it?
Why six and not one

Because each boundary is a place you can change one side without touching the other. Retargeting this compiler from MIPS to ARM means rewriting phase 6 and nothing else. Adding a while loop means touching phases 1–4 and nothing in 5 or 6. You will do both of those things this semester, and you will only be able to do them quickly because the boundaries exist.

Phase 1 in one picture

The scanner reads characters and emits tokens. A token is three things: what KIND of thing it is, the exact TEXT that matched, and WHERE it was.

    source :   count  =  count + 1 ;

    tokens :   ID(count)   ASSIGN   ID(count)   PLUS   NUM(1)   SEMI
               │           │                                    │
               │           │                                    └─ line 4, col 19
               │           └─ kind only; the text "=" is not needed again
               └─ kind AND text: the parser will need the name "count"

The KIND is what the parser makes decisions on. The TEXT matters only for identifiers and numbers — nobody ever needs to be reminded that SEMI was spelled ;. The LOCATION is what turns syntax error into line 12, column 7: missing semicolon, and that difference is most of what people judge a compiler by.

Watch it happen

The scanner starts at the first character. Nothing has been recognised yet.

int total;
^

tokens: (none)

It matches the longest thing it can from here. Three characters spell a keyword.

int total;
^^^

tokens: INT

Whitespace matches a rule whose action is to produce no token at all — but it still has to advance the column counter.

int total;
   ^

tokens: INT

Five letters. This matches the identifier pattern, and no keyword.

int >>>total;
    ^^^^^

tokens: INT  ID(total)

One punctuation character, one token. The scanner is done; the file ends.

int total>>>;
         ^

tokens: INT  ID(total)  SEMI

The two rules that decide everything

Flex builds a finite automaton from your rules and runs all of them at once. When several rules could match, two rules break the tie, in this order:

1. Longest match wins

Given <=, the rule for <= beats the rule for <, because it consumes two characters instead of one. Where those rules appear in the file makes no difference at all.

    input:  a <= b

    with a "<=" rule:      ID(a)  LE  ID(b)          3 tokens
    without a "<=" rule:   ID(a)  LT  ASSIGN  ID(b)  4 tokens  ← parser will choke

2. On a tie, the earlier rule wins

Given int, the keyword rule and the identifier rule both match exactly three characters. Now — and only now — order decides. This is the entire reason keyword rules must be written above the identifier rule, and it is worth proving to yourself by breaking it.

A scanner has the identifier rule written ABOVE the keyword rules. What does it return for the input while?

What the scanner deliberately does not do

It is worth being precise about the boundary, because half the confusion in this course comes from expecting one phase to do another phase's work.

The scanner DOESThe scanner does NOT
Recognise while as a keywordKnow that a while needs a condition after it
Recognise ) as a delimiterCheck that parentheses balance
Recognise total as an identifierKnow whether total was declared
Report @ as not being in the languageReport int int int; as wrong

Every entry in the right-hand column belongs to a later phase. int int int; is three perfectly good tokens; it is the parser, in Topic 2, that will object.

Errors are a feature, not an afterthought

A scanner that stops at the first bad character makes the programmer recompile once per typo. Ours reports every lexical error in one run and keeps going. That costs about four lines:

    .   {
            fprintf(stderr,
              "  LEXICAL ERROR  line %d, col %d: "
              "character '%s' is not part of this language\n",
              lineNo, colNo, yytext);
            lexErrorCount++;   /* count it   */
            colNo++;           /* step past it */
                               /* and CONTINUE */
        }
Column numbers are not free

Flex tracks lines for you with %option yylineno. It does not track columns. If you want a column number — and you do — you have to advance a counter yourself in every action, including the ones for whitespace and comments. Forget the comment case and every line number after your first multi-line comment will be wrong.

The same input, four ways

Here is what each phase will make of one line of source. You are building the first column this week; the rest arrive over the next four topics.

int total;
total = 2 + 3;
print(total);
INT  ID(total)  SEMI
ID(total)  ASSIGN  NUM(2)  PLUS  NUM(3)  SEMI
PRINT  LPAREN  ID(total)  RPAREN  SEMI
STMT_LIST
  DECL: int total
  ASSIGN: total
    BINOP: +
      NUM: 2
      NUM: 3
  PRINT
    VAR: total
DECL int total
t0 = 2 + 3
total = t0
PRINT total
    li   $t0, 2
    li   $t1, 3
    add  $t2, $t0, $t1
    sw   $t2, 0($sp)      # total
    lw   $a0, 0($sp)
    li   $v0, 1
    syscall
Why is the TAC not just total = 5 ?

It will be — but not yet. Constant folding happens in phase 5, and phase 4's job is a faithful, unclever translation. Mixing the two is how compilers get bugs that only appear when optimization is on.

This week's project

Project 1 asks for a lexical analyzer that recognises every token in the language, reports errors with their exact location, and certifies a file when it is clean. Four things are worth knowing before you start:

  1. Scan the whole language now, not just Topic 2's part of it. Recognising switch in week 1 costs one line and saves you editing this file in week 12.
  2. The token KINDS you choose become bison's %token declarations in Topic 2. Name them carefully; you will type them several hundred times.
  3. Make the error messages good. They are the part of this project you will still be using in December.
  4. Exit non-zero on failure. It is what lets make and a test script tell success from failure without reading your output.
