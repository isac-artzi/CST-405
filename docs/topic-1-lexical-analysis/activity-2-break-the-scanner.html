Break the Scanner on Purpose

Five experiments that each break the scanner in one specific way. Predict first, then run.

All topics  ›  Topic 1  ›  Activity 2
Format pairsTime 45 minBring a working build of the Topic 1 lexer

The point

Four experiments, each of which breaks the scanner in a specific way. Predict the outcome first, then run it. A prediction you got wrong teaches more than three that you got right, so write the prediction down before you run anything — otherwise you will remember having predicted correctly.

Work on a copy

cp -r instructor/topic-1-lexical-analysis/lexer /tmp/broken and vandalise that. You want the original intact for comparison.

The experiments

  1. Move the identifier rule above the keyword rules. Predict what tests/03_keywords_vs_ids.cm will produce, then run it. Which of the two tie-breaking rules did you just change, and why did longest match not save you?
  2. Delete the "<=" rule. Predict the token count for tests/02_longest_match.cm, then run it. You should be able to say the exact number before you look.
  3. Move the "<" rule above "<=" (with both present). Predict, then run. This one surprises people — explain in one sentence why nothing changed.
  4. Make the error action call exit(1) instead of counting and continuing. Run tests/05_lexical_errors.cm, which contains four bad characters. How many did you find out about? Now imagine that file is 4,000 lines long.
  5. Delete the skip() call from the block-comment rule (leave the rule itself). Run tests/04_comments.cm and look at the line numbers. This is the bug the header comment in that test warns you about — now you have seen it.

One design question, no experiment

Our language has no string literals. Suppose you wanted to add them: print("total = ");

  • What pattern would match a string literal? Write it.
  • What should happen if the closing quote is missing before end of line?
  • Which phase should reject "abc" + 1 — the scanner, the parser, or the semantic analyzer? Defend your answer in one sentence.
A hint on the third question

Ask what each phase can actually see. The scanner sees one token at a time and has no idea what surrounds it. The parser sees the shape of the expression but knows nothing about types. Only one phase in this course is in a position to notice that a string and an integer cannot be added.

Deliverable

Extend activity1.md (or start activity2.md) with:

  • for each of the five experiments: your written prediction, what actually happened, and one sentence reconciling them;
  • your answers to the three string-literal questions;
  • one sentence on which experiment surprised you most and why.

This material shows up directly in Lab Questions 1 and 2 and in your Project 1 video — the video asks you to explain design practices and implementation strategies, and 'here is what happens when you get rule order wrong' is exactly that.
