Arrays, Functions, and the Activation Record

Three new language features, one new idea — and the new idea is where every call, every local variable and every recursion lives.

Precedence is a table, not a grammar rewrite

You could encode precedence by layering the grammar — expr → term → factor. Bison lets you keep one flat rule and declare the precedence instead. Both work; the declaration is shorter and keeps the grammar readable.

%left  '+' '-'      /* lowest  — and LEFT associative     */
%left  '*' '/'      /* higher                                */
%right UMINUS       /* highest — and RIGHT associative        */

expr : expr '+' expr | expr '-' expr
     | expr '*' expr | expr '/' expr
     | '-' expr %prec UMINUS
     | '(' expr ')'  | NUM | ID ;

Two things are being declared at once, and they are independent:

  • Precedence — later lines bind tighter. This is what makes 2 + 3 * 4 parse as 2 + (3 * 4).
  • Associativity — %left makes 17-5-3 group as (17-5)-3, which is 9. %right would give 17-(5-3), which is 15. Subtraction is not associative, so this choice is not cosmetic.
%prec UMINUS is not decoration

Without it, the rule '-' expr inherits the precedence of BINARY minus, which is lower than *. Then -2 * 3 parses as -(2 * 3). For multiplication the answer happens to be the same; for a function call with side effects, or for division, it is not. Try removing it and parsing -8 / 2 / 2.

Given %left '+' '-' then %left '*' '/', how does a - b * c - d parse?

Arrays are address arithmetic

An array is a block of consecutive words. a[i] means the word at (base of a) + i×4. That is the whole idea; everything else is bookkeeping about where the base is.

int scores[4];        scores lives at  8($sp)

   memory:      8($sp)   12($sp)   16($sp)   20($sp)
                ┌───────┬─────────┬─────────┬─────────┐
                │ [0]   │ [1]     │ [2]     │ [3]     │
                └───────┴─────────┴─────────┴─────────┘

   scores[i]  ->   addi $t0, $sp, 8      # base
                   sll  $t1, $ti, 2      # i * 4
                   add  $t0, $t0, $t1    # base + offset
                   lw   $t2, 0($t0)

The interesting part is that the base is found three different ways depending on what kind of array it is — and telling those apart is most of the array work in codegen.c:

KindWhere the elements areHow to get the base
global int g[4];the .data sectionla $t0, g_g
local int a[4];this function's frameaddi $t0, $sp, off
parameter int a[]somebody else's frame or .datalw $t0, off($sp)
Why an array parameter has no size

Arrays are passed by REFERENCE: the caller hands over the base address, one word, and the callee's slot holds that address rather than the data. That is why int a[] takes 4 bytes in the frame no matter how big the array is, and why the callee cannot know its length — which is why every function that takes an array in this language also takes a count.

The activation record

This is the one genuinely new idea in Topic 3. Every call needs somewhere to put its parameters, its locals, and the address to return to. That somewhere is a block of stack pushed on entry and popped on exit.

        high address
        ┌──────────────────────────────┐
        │ saved $ra                    │   frameSize-4($sp)
        ├──────────────────────────────┤
        │ (alignment)                  │
        ├──────────────────────────────┤
        │ parameters                   │
        │ locals and arrays            │   0($sp) .. localBytes-1
        │ compiler temporaries         │
        └──────────────────────────────┘   <- $sp
        low address

main is running. Its frame holds its own locals.

$sp ──> ┌──────────────┐
        │ main's frame │
        └──────────────┘

main calls sum(a, 4). First the arguments go into $a0-$a3, while the $t registers are still valid.

    move $a0, $t3      # base address of a
    li   $a1, 4

$sp ──> ┌──────────────┐
        │ main's frame │
        └──────────────┘

Then everything live is written back to memory, because $t0-$t9 are caller-saved: the callee is free to clobber them all.

    sw   $t2, 4($sp)   # write back before the call
    jal  fn_sum

The prologue of sum pushes a NEW frame and saves the return address into it. Now two frames are live.

    addi $sp, $sp, -24
    sw   $ra, 20($sp)

$sp ──> ┌──────────────┐
        │ sum's frame  │   locals of sum
        ├──────────────┤
        │ main's frame │   untouched
        └──────────────┘

sum stores its parameters from $a0-$a3 into its own frame, because it will need $a0-$a3 again if it calls anything.

    sw   $a0, 0($sp)   # parameter a
    sw   $a1, 4($sp)   # parameter n

On return: the value goes in $v0, then control jumps to the epilogue — it does not fall through.

    move $v0, $t1
    j    fn_sum__epilogue

The epilogue restores $ra, pops the frame, and returns. main's frame is exactly as it was.

fn_sum__epilogue:
    lw   $ra, 20($sp)
    addi $sp, $sp, 24
    jr   $ra

$sp ──> ┌──────────────┐
        │ main's frame │
        └──────────────┘
Three bugs that all look like 'my compiler is haunted'
  • Not saving $ra. Works for one call. Breaks the moment a function calls another function, and breaks spectacularly on recursion, because jal overwrites $ra every time.
  • Not pushing a new frame. The callee's locals land on top of the caller's. Your variables change value across a call for no visible reason.
  • Falling through on return instead of jumping to the epilogue. A return in the middle of a function silently continues into the code after it. Symptom: a function that always returns whatever its LAST return statement says.

Scope is a stack

Topic 2 had one flat set of names. Now a name can mean different things in different places, and the rule is: innermost wins.

int n;                 <- global

int show(int n) {      <- parameter shadows the global
    return n;
}

int main() {
    n = 1;
    print(n);          <- the global:    1
    print(show(2));    <- the parameter: 2
    print(n);          <- the global again, untouched: 1
    return 0;
}
  [1] function show : n
  [0] global         : n, show, main

  lookup("n") searches [1] first, finds the parameter, stops.
  [1] function main : (no locals)
  [0] global        : n, show, main

  lookup("n") searches [1], finds nothing, falls through to [0].

Two symbol tables now exist and they answer different questions. semantic.c keeps a scope stack that answers is this name visible here? and is thrown away when analysis finishes. symtab.c keeps a storage map that answers what address is this name? and is rebuilt per function during code generation. Confusing them is the single most common source of confusion in this topic.

Two passes, not one

This program is legal, and it forces a design decision:

int main() {
    print(helper(3));       <- helper is used here...
    return 0;
}
int helper(int x) {         <- ...and defined here
    return x + 1;
}

A single pass over the AST would reach the call before it had ever seen the definition. So performSemanticAnalysis runs twice: pass 1 records every function signature, pass 2 checks every body. Collapse them into one pass and the program above stops compiling — which is a perfectly defensible language design (C required forward declarations for exactly this reason), but it should be a decision, not an accident.

What pass 1 has to record, and what it does not

It needs the name, the parameter count, and which parameters are arrays — everything needed to check a CALL. It does not need to look inside the body at all. That asymmetry is why two cheap passes beat one clever one.

Interview questions this topic answers

Topic 3 includes a technical interview, and these are the questions it is actually about. Practise saying the answers out loud.

  • How does your parser tell a variable declaration from a function declaration? (Both start int ID — what is the deciding token?)
  • Where do local variables live, and who allocates them?
  • What exactly happens between jal and the first instruction of the callee?
  • Why is $ra saved in the frame rather than kept in a register?
  • Your language passes arrays by reference and integers by value. Why not both the same way?
