Draw the Activation Record

Predict the stack frame, check it against the generated assembly, then sabotage the epilogue.

All topics  ›  Topic 3  ›  Activity 3
Format pairsTime 50 min

The point

Draw the stack frame you expect, then hold the generated assembly up against it. This is the activity that makes function calls stop being magic.

Do this

  1. Draw the frame you expect the compiler to build for
    int addUp(int a, int b) {
    int t;
    t = a + b;
    return t;
}
    Label every slot with its offset from $sp and say how many bytes the whole frame is. Do not forget the temporaries.
  2. Compile it WITHOUT -q and find the line that says Activation record for 'addUp': N bytes, followed by the symbol table. Compare with your drawing.
  3. Read the prologue and epilogue in the generated .s. Account for every instruction. There should be no line you cannot explain.
  4. Now sabotage the epilogue. Comment out the lw $ra restore in emitEpilogue. Predict what happens, then rebuild and run. Where does control actually go?
  5. Sabotage differently. Restore that, and instead make TAC_RETURN NOT jump to the epilogue — just set $v0 and fall through. Test with a function that has a return in the middle. Explain the result.

Deliverable

Your predicted frame diagram next to the compiler's symbol table, an annotated prologue/epilogue, and one paragraph for each sabotage explaining the failure mode. Step 5 is exactly the bug that broke return inside a switch in an earlier version of this compiler.
