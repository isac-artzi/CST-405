The language

\n

This is the entire starter language. Three kinds of statement, one operator, one type.

\n
program    ->  stmt_list\nstmt_list  ->  stmt  |  stmt_list stmt\nstmt       ->  decl  |  assign  |  print_stmt\ndecl       ->  \'int\' ID \';\'\nassign     ->  ID \'=\' expr \';\'\nexpr       ->  NUM  |  ID  |  expr \'+\' expr\nprint_stmt ->  \'print\' \'(\' expr \')\' \';\'
\n

It looks trivial, and as a language it is. As a compiler project it is not, because a working compiler for this language needs every one of the six phases, complete. Adding * later costs one grammar rule. Adding the first phase costs four weeks.

\n
What you are really building

The scaffolding. Everything in Topics 3–6 is a new case in switch statements you write this month. Get the shape right now and the rest of the semester is additive; get it wrong and you will rewrite it in November under deadline.

Phase 2 — the parser, and what a semantic action really is

\n
\n

Bison builds a bottom-up parser. It shifts tokens onto a stack and, whenever the top of the stack matches the right-hand side of a rule, REDUCES: pops those symbols and pushes the left-hand side. The action in braces runs at the moment of the reduction, and that is when your AST node gets built.

\n
expr : expr \'+\' expr   { $$ = createBinOp(\'+\', $1, $3); }\n       ─┬─  ─┬─  ─┬─           ─┬─              ─┬─  ─┬─\n        │    │    │             │                │    └── $3, the right subtree\n        │    │    └── $3        │                └─────── $1, the left subtree\n        │    └── $2 (unused)    └── the value THIS rule hands back\n        └── $1
\n

Because reductions happen innermost-first, the children are already built by the time the parent\'s action runs. You never write tree-building code that walks anything; you only ever assemble one node from pieces that already exist.

\n

Input: total = 2 + 3 ; — the parser starts with an empty stack.

stack: (empty)                 remaining: ID = NUM + NUM ;
\n

Shift ID, then \'=\' , then NUM.

stack: ID  =  NUM              remaining: + NUM ;
\n

NUM can be reduced to expr. The action runs: $$ = createNum(2).

stack: ID  =  expr             remaining: + NUM ;\n\n       expr ─ NUM: 2
\n

Shift \'+\' and NUM; reduce that NUM to expr as well.

stack: ID  =  expr  +  expr    remaining: ;\n\n       expr ─ NUM: 2      expr ─ NUM: 3
\n

Now the top three symbols match expr \'+\' expr. Reduce, and the action builds the BINOP node from two subtrees that already exist.

stack: ID  =  expr             remaining: ;\n\n       expr ─ BINOP: +\n                ├─ NUM: 2\n                └─ NUM: 3
\n

Shift \';\' and reduce the whole thing to assign. One statement, one tree.

stack: assign                  remaining: (none)\n\n       ASSIGN: total\n         └─ BINOP: +\n              ├─ NUM: 2\n              └─ NUM: 3
\n
\n

Parse tree vs AST — the difference that matters

\n

The parse tree records every reduction the parser made, including the ones that exist only to encode precedence. The AST records what the program MEANS. Compare, for total = 2 + 3;:

\n
assign\n├─ ID(total)\n├─ \'=\'\n├─ expr\n│  ├─ expr\n│  │  └─ NUM(2)\n│  ├─ \'+\'\n│  └─ expr\n│     └─ NUM(3)\n└─ \';\'
\n
ASSIGN: total\n└─ BINOP: +\n   ├─ NUM: 2\n   └─ NUM: 3
\n
\n

The AST threw away the semicolon, the equals sign, and the chain of single-child expr nodes. Nothing downstream needs them. Every later phase walks the AST, so every node you keep is a node five phases have to handle.

\n

Phase 3 — semantic analysis is where \'it parses\' stops being enough

\n
\n

These two programs are equally legal as SENTENCES. Only one of them means anything.

\n
int x;              int x;\nx = 1;              x = ghost;      <- parses fine: ID \'=\' expr \';\'\nprint(x);           print(x);       <- but `ghost` was never declared
\n', '

No context-free grammar can express \'declared before use\', because the declaration can be arbitrarily far away. That is precisely the boundary between phase 2 and phase 3, and it is worth being able to state crisply in a technical interview.

\n

The symbol table is what closes the gap. Walk the AST; on a declaration, insert; on a use, look up.

\n

Phase 4 — three-address code, and why bother

\n
\n

You could generate MIPS straight from the AST. People do. But every optimization you will write in Topic 4 wants a flat list of simple instructions, not a tree — and every new target machine you might add wants to start from something that is not the source language.

\n
AST                            TAC\n                               t0 = 2 + 3\nASSIGN: total          ->      total = t0\n  BINOP: +\n    NUM: 2                     one operator per instruction,\n    NUM: 3                     at most three operands
\n
The rule that makes the recursion work

generateTACExpr() returns the NAME of the place holding the result. Sometimes that is a literal ("5"), sometimes a variable ("total"), sometimes a temporary ("t0"). The caller does not care which — it just uses the name. One return convention, and the whole tree walk falls out.

\n
\n

Phase 6 — registers are a cache over memory

\n
\n

TAC pretends it has unlimited named locations. MIPS has 32 registers. The resolution is simple and it is the same one CPUs use for main memory: give every name a permanent HOME in the stack frame, and treat $t0–$t9 as a cache over those homes.

\n
SituationWhat the allocator does
Need a value that is already in a registeruse it; no instruction emitted
Need a value that is notlw from its home slot
About to overwrite a nametake a register, mark it dirty, do NOT load
No free registersevict the least recently used one, sw it first if dirty
About to call a functionwrite back everything dirty; the callee owns $t0-$t9
\n

Because every name has a home, any value can be written back at any moment. That one guarantee is what makes spilling safe, and it is why layoutFrame() walks the whole function before a single instruction is emitted.

\n

The second costs one error production per statement form. Lab Question 5 asks you to write a program with three deliberate syntax errors and demonstrate that you detect all three with their exact locations — so this is not optional polish, it is the assignment.

\n
How an error production works

Bison has a magic token, error. Writing | ID \'=\' expr error tells it: if you were parsing an assignment and hit something unexpected where the semicolon should be, take this rule instead, run its action, and then call yyerrok to resume normal parsing. The action is where you print a message that names the statement you were in.

\n
assign:\n    ID \'=\' expr \';\'      { $$ = createAssign($1, $3); free($1); }\n  | ID \'=\' expr error    { fprintf(stderr,\n                             "line %d: missing \';\' after assignment to \'%s\'\\n",\n                             yylineno, $1);\n                           free($1); $$ = NULL; yyerrok; }\n  ;

The single most common way this goes wrong

Leaving code generation until week 5. Phases 4 and 6 are where the design decisions you made in week 2 come due, and if the AST is the wrong shape you want to find out in week 3, not the night before the deadline. Get one statement — print(1); — all the way through to running MIPS in the first week. Then widen.
