Measure It, Document It, Defend It

No new syntax this week. The compiler is finished; the question is whether you can say anything true about it.

What is left

Every language feature is in. Topic 6 adds nothing to the grammar. What it adds is the three things that separate a project from a piece of engineering: numbers, documentation, and an honest account of the limits.

Two different performance questions

The Benchmark project asks for compilation time and execution time. They measure different things and they are answered with different tools.

QuestionWhat you measureHow
How fast does the compiler run?wall-clock time per phasethe timing table the driver already prints
How fast does the compiled code run?instructions executedSPIM's instruction count, optimized vs unoptimized
How big is the compiled code?TAC and MIPS instruction countsthe optimizer's own scorecard

Compilation time

The driver already reports it. Run it on inputs of several sizes and look at the SHAPE of the curve, not one number:

  Compilation time by phase
    1. Lexical + syntax analysis      0.07 ms
    2. AST construction               0.00 ms
    3. Semantic analysis              0.10 ms
    4. Intermediate code (TAC)        0.65 ms
    5. Optimization                   0.33 ms
    6. MIPS code generation           0.36 ms
    TOTAL                             1.55 ms
The question worth asking about that table

Which phase grows fastest as the input grows? Compile a 10-line, a 100-line and a 1000-line program and plot it. Most phases here are linear in program size. The optimizer is not — it runs to a fixed point, and isReadLater() scans forward from every instruction, which makes dead-code elimination quadratic. Finding that yourself, in your own compiler, is a much better write-up than repeating that optimization is expensive.

Execution time

Instruction count is the right metric here — it is deterministic, and SPIM is not a timing-accurate simulator, so wall-clock numbers from it mean very little.

  # optimized vs unoptimized, same source
  TAC instructions       48 -> 31       35.4% smaller
  MIPS instructions     112 -> 74       33.9% smaller
  Instructions executed  8,431 -> 5,102 39.5% fewer

Report all three. They will not agree, and the disagreement is informative: code size and work done diverge exactly in proportion to how much of the removed code was inside a loop.

Honest measurement

Three rules that separate a number you can defend from a number you cannot:

  1. Repeat the run. Three times, minimum. If the spread is 8%, then a 5% improvement is not a result.
  2. Say what you compared. 'Optimized vs unoptimized, same source, same machine, same simulator' — not 'my compiler is 30% faster', which is faster than what?
  3. Report the benchmark. A speedup on a program with a hot loop tells you about hot loops. Include the source you measured.

Your optimizer reports 35% fewer TAC instructions, but SPIM reports only 4% fewer instructions executed. What is the most likely explanation?

'Three things you would do differently' is not a confession, it is a design review. Pick one from the compiler's architecture, one from the language's features, and one from your implementation — and for each, say what it would have cost to do differently and why you did not.

What a README has to contain

Somebody who has never seen your compiler must be able to build and run it from your README alone. That is the whole test.

# <name> — a compiler for <language>

## What it does
One paragraph. What language it accepts, what it emits.

## Requirements
flex 2.6+, bison 2.3+ (or byacc), gcc, SPIM or QtSPIM
Tested on: <your OS and versions>

## Build
    make

## Run
    ./minicompiler input.cm output.s
    spim -file output.s

## The language
The grammar, in BNF. Every construct with one example.

## How it works
The six phases, one paragraph each, naming the file.

## Performance
The measurement table. Say what you compared and on what.

## Known limitations
The honest list. Each with a reason.

## Team
Who wrote which phase.

                             files" is not

The video

Each team member records their own. The rubric asks for the compiler working, plus decisions about language design and implementation approach. A structure that works:

  1. Show it run (60s). A non-trivial program, compiled, then executed in SPIM. Start here — everything after this is commentary on something the viewer has already seen work.
  2. Follow one construct through all six phases (3–4 min). Pick something with structure — a loop or a switch — and show it as source, tokens, AST, TAC, optimized TAC, and MIPS. This is the single most convincing thing you can do.
  3. Your part (2 min). Which phases you wrote, and one problem you had to solve, with the code on screen.
  4. A decision you made (2 min). Short-circuit or eager? Jump table or linear chain? Desugar for or lower it directly? Say what you chose and what would change your mind.
  5. Numbers and limits (1–2 min). The measurement table, and two limitations with reasons.
The failure mode to avoid

Reading the code aloud. The viewer can read. What they cannot get from the repository is WHY it is shaped that way — which alternatives you considered, what broke, what you would do differently. Ten minutes of that is worth an hour of narration.

A last look back

Fifteen weeks ago the scanner returned a token. Everything since has been the same move repeated: choose a representation, define what the phase before must hand you, and translate. The compiler is now about 3,000 lines. Roughly 85% of it does not know what machine it targets, and that is the part worth being proud of.

If you want to keep going
  • Types. Add bool or float. The work is almost entirely in phase 3, and it will show you why real compilers have a type system rather than a type field.
  • A control-flow graph. Build one from the TAC. Then liveness, then register allocation by graph colouring — the textbook path, and each step is visibly better than what you have.
  • An ARM back end. You already know it is one file.
  • LLVM IR instead of MIPS. Emit textual LLVM from your TAC and let clang do the rest. Two hundred lines, and suddenly your language runs natively on any machine LLVM targets.
