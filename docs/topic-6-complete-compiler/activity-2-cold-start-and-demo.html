Cold-Start README Test and Demo Dry Run

Somebody who has never seen your compiler tries to build it. Then you explain it out loud and they interrupt.

All topics  ›  Topic 6  ›  Activity 2
Format groups of threeTime 50 minBring a draft README and a laptop you can wipe

The point

Two things get checked here, and both are checked by somebody who is not you: can a stranger build your compiler, and can you explain it out loud.

Part 1 — the cold-start README test (25 min)

  1. Swap repositories. Clone a group member's compiler into a fresh directory. Do not ask them anything.
  2. Follow their README literally. Every place you had to guess, improvise, or ask — write it down. Those are bugs in the README.
  3. Score it. Could you build it? Could you run it on your own input file? Could you find out what the language accepts without reading parser.y? Did the limitations section tell you anything you then confirmed?
  4. Hand back your list. Fix your own README before you leave.

Part 2 — the demo dry run (25 min)

Eight minutes each, to the other two, following the structure in the lecture notes. The audience's only job is to interrupt with why.

  1. Show it run before you explain anything.
  2. Follow one construct through all six phases. Have the files open already; do not spend demo time navigating.
  3. Name a decision and defend it. The audience should push back once.
  4. Give two limitations with reasons.
  5. Audience feedback: one thing that was convincing, one thing that was not, one question you would have asked if there were time.
The most common demo mistake

Explaining for six minutes and demonstrating for one. Lead with the working program. Everything after it lands differently once the viewer has seen the thing actually work.

Deliverable

The list of README problems you found in someone else's, the list they found in yours, and your fixed README. Plus your written notes from the demo feedback — those go straight into your recorded video.
